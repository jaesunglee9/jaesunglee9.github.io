Mounting Google Drive on Linux

I hope this article can help people who want to mount Google Drive as a folder on Linux, There are mcp for remote access I believe, but they are clunky and slow. On the other hand, this way is much more dangerous, and automatic, daily(maybe even hourly) backup is highly recommended.

Note that I am using Guix System Distribution, but the below method should be applicable to most linuxes.

The setup has two parts: authorize rclone to access Drive, then mount a folder. Authorization alone does not create a local directory.

Install and verify

Install rclone using your distribution's package manager or follow the upstream installation instructions. Check that the installed build supports rclone mount and that FUSE is available.

On Guix, I initially installed the packages with: 

guix install rclone restic
rclone version
restic version

Guix users should consider putting the packages inside Guix home configuration.

Use my own Google OAuth client

Following rclone's client-ID guide:

  1. Create or select a Google Cloud project and enable Google Drive API.
  2. Configure OAuth branding, contact email, audience, and data access.
  3. For a personal external app in Testing, add my account as a test user.
  4. Create an OAuth client of type Desktop app; retain its ID and secret.
  5. Follow the guide's production-status requirements before unattended use.

Google says external apps in Testing receive refresh tokens that expire after seven days when requesting Drive scopes. Production status does not prevent all other causes of token expiry. See Google's token-expiration documentation.

Run the wizard: 

rclone config

Create gdrive with storage type drive, enter the custom client credentials, and authorize in the browser. For an existing remote, edit its credentials and replace the token through the wizard. Preserve the existing remote name. See rclone's configuration instructions.

For reading existing files, choose drive.readonly. Choose drive when writes are needed; drive.file does not grant access to every existing file. These are permissions granted to rclone by Google, separate from the mount's --read-only flag. See Google's scope definitions.

Access from a terminal

These commands address the remote directly, without a mount: 

rclone listremotes
rclone lsf gdrive: --max-depth 1
rclone lsf 'gdrive:some-folder' --max-depth 1

Paths containing spaces need shell quotes. To inspect one plain-text file: 

rclone cat 'gdrive:some-folder/example.txt'

Any terminal on this configured machine can use the remote. Another machine needs rclone and its own configuration/authorization. On a headless host, answer no to browser authentication and follow the wizard's instructions on abrowser-equipped machine. See rclone's remote setup guide.

rclone config file shows the configuration location. Treat it as sensitive because it holds tokens. Do not paste it into a blog or commit it to Git. Avoid placing credentials in examples, screenshots, or command history.

Mount for tools that expect file paths

I use ~/gdrive as the mount point. Start with read-only access: 

mkdir -p ~/gdrive
rclone mount gdrive: ~/gdrive --read-only --vfs-cache-mode full

This command stays in the foreground. Keep the terminal open while using the mount.

Read-only access for AI agents

If an agent only needs to read documents, --read-only is a useful guardrail: it cannot overwrite or delete files through this mount. It can still read and copy their contents, so this does not protect against disclosure.

The important catch: a read-only mount is not a sandbox. An agent with access to writable rclone credentials can bypass it by calling rclone directly. For stronger separation, give the agent only read-only credentials and isolate it from the full-access configuration, for example under a separate OS user. Naming another remote "readonly" is not enough.

A writable background mount

For my own work, I want to edit files too. Unmount any existing mount first, then omit --read-only: 

mkdir -p ~/gdrive ~/.local/state/rclone
rclone mount gdrive: ~/gdrive \
  --vfs-cache-mode full \
  --daemon \
  --log-file ~/.local/state/rclone/gdrive.log \
  --log-level INFO

If gdrive was authorized with drive.readonly, edit it with rclone config, choose the drive scope, and authorize it again. Removing a mount flag cannot expand Google's granted permissions or make someone else's read-only shared file writable.

Writable access means edits, renames, and deletions can affect the real Drive files. That includes actions taken by an agent using this directory. Keep versioned backups before handing it that access.

--daemon runs the mount in the background; it does not arrange startup after reboot or restart after a crash. Logs go to ~/.local/state/rclone/gdrive.log. To use the same background setup read-only, add --read-only back.

With the VFS cache, saving locally is not immediate confirmation of an upload. Files must close and the write-back delay must pass; check the log before shutting down. See rclone's mount documentation.

Unmounting and recovering a disconnected mount

For a healthy mount, finish writes and unmount normally: 

fusermount -u ~/gdrive

If accessing the directory reports Transport endpoint is not connected and the mount process has died, detach the stale mount before running the mount command again: 

fusermount -uz ~/gdrive

This detaches the mount; it does not delete Drive files. It is not a way to flush pending uploads. Some distributions call the command fusermount3 instead.

Google-native documents

Google-native documents are exported representations. An exported document is not a live Google Docs editing session. See Google's export documentation. Rclone notes that native Docs can appear as zero bytes through a mount; use explicit downloads when mount access fails. See rclone's Docs limitations.

Mounting, copying, and syncing

I wanted mounted access. A mount retrieves remote content as applications use it; its cache is not a complete offline replica or a backup.

Operation Purpose Deletions
mount Expose remote files through a directory Writable operations affect Drive
copy Transfer new or changed files Does not remove extra destination files
sync Make destination match source Can delete destination-only files
bisync Reconcile changes in both directions Can propagate deletions both ways

To download a folder, first inspect a dry run: 

rclone copy 'gdrive:some-folder' ~/DriveDownloads/some-folder --dry-run

Remove --dry-run when the source and destination are intended. Copy can overwrite changed destination files; retaining extra files is not versioning. See copy, sync, and bisync.
