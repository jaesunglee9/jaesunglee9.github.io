URL Shortener V2: Survive an application-machine failure

A link can be safely stored and still be unusable. In V1, the application server is the only way to reach it. Stop that process and every redirect stops, even though the database is healthy.

We'll give requests another route to the same data. The interesting part is what happens between a server failing and the rest of the system noticing.

Define what surviving a failure means

Traffic remains about four creations and forty redirects per second during a busy period. Storage growth is unchanged. The new requirement is that one failed application server must not cause an outage that lasts until somebody repairs it.

Failure detection is not instantaneous. A request already running on a failed server can fail, and a few new requests can reach it before health checks remove it. Our goal is to recover routing automatically after a bounded detection period. Planned deployments should avoid that failure window by draining requests before stopping a server.

This is a more useful contract than promising that every request will succeed through any failure. We can measure the detection time, failed requests, and surviving capacity separately.

Two application instances, one set of mappings

Place a load balancer in front of two instances on different machines: 

                         +-> application A --+
client -> load balancer -+                   +-> database
                         +-> application B --+

The load balancer chooses a healthy instance for each request. It does not need to send a visitor to the instance that created the link.

For example, A can create a mapping and B can later resolve it. Both use the same database and the same interpretation of a short code. The candidate-generation and primary-key rules from V1 already allow concurrent writers.

This is what “stateless application instances” means here. They still have memory, connection pools, and temporary work. But losing that local state must not lose an acknowledged mapping or make a request valid only on one instance. An in-memory map of newly created links would violate that property.

A load balancer also needs a failure strategy. For this article we assume a redundant or managed balancer and place the application instances in separate machine failure domains. Running both processes on one host would not satisfy the requirement. Losing a whole region and losing the database remain separate problems.

Walk through an unplanned failure

Consider a balancer that checks readiness every five seconds and removes a target after two failed checks. These are illustrative settings, not a recommended configuration for every deployment. 

t0       A and B pass readiness checks.
t1       A crashes just after its last successful check.
t1..t2   Some requests still go to A and fail.
t2       A has failed enough checks; the balancer removes it.
t3       New requests go to B.
t4       A is repaired and passes the recovery checks.
t5       A re-enters the target set.

The vulnerable interval depends on where the crash falls between checks, how long a check may wait, and how quickly routing changes propagate. Multiplying interval by failure count is only a rough estimate; test the observed interval with the selected balancer.

An in-flight request does not move to B when A dies. The connection may close or time out. A client can retry a lookup, but creation has the ambiguous-commit case from V1. A proxy must not blindly replay a creation request unless the API provides the required idempotency semantics.

Even for reads, retries need a deadline and a small attempt budget. If every layer retries independently, one client request can turn into many attempts during a failure. AWS's discussion of retries explains this amplification and why backoff alone is insufficient without limits.

A useful health check asks a narrow question

A readiness endpoint should answer whether this instance can currently accept useful traffic. It should stay unready until configuration, routing, and required local initialization are complete.

Liveness asks a different question: is the process stuck in a state that needs a restart? Treating a temporary database outage as evidence that every application process needs restarting can turn one dependency failure into a restart storm.

We therefore keep a simple process liveness check and use readiness to control routing. Database connectivity also deserves monitoring, but a shared database failure cannot be solved by switching between A and B. If readiness includes a database probe, its timeout and its behavior when every instance fails must be deliberate.

Balancer behavior is product-specific. For example, AWS Application Load Balancer can fail open when every registered target is unhealthy. We must verify our chosen balancer's behavior instead of assuming that “unhealthy” always means no traffic.

Can B actually carry the service?

In normal operation each instance sees roughly half the requests. After A fails, B sees the full load.

Suppose a load test of this request mix were to show that one instance can handle eighty requests per second within the chosen latency budget. That would leave room for the roughly forty-four requests per second expected after a failure. Eighty is an example measurement for the calculation, not a result from this project.

The general check is: 

capacity remaining after one failure >= peak admitted traffic

Connection pools need the same attention. Two pools of twenty database connections can consume forty connections; adding ten instances can multiply that again without increasing database capacity. Keep a total connection budget, bound local concurrency, and reject excess work before queues grow without limit.

Watch latency and failures during the transition, not just CPU before the failure. A survivor with a cold runtime or a burst of new connections may behave differently from one already serving steady traffic.

Deploy without abruptly cutting connections

A planned replacement gives us time to drain A:

  1. Start the replacement and wait for it to become ready.
  2. Stop assigning new requests to A.
  3. Let A finish existing requests, up to a drain deadline.
  4. Stop A, then repeat for the next instance.

The drain deadline prevents one stuck request from blocking a deployment forever. Requests still running at the deadline can fail, so the application and balancer deadlines must fit together.

Old and new application versions overlap during this process. Database schema changes must support that overlap. For example, add a new optional column before code starts using it, and remove an old column only after old instances are gone. Otherwise “rolling deployment” can still produce a service-wide error.

What would demonstrate that this works?

Create a link through A and read it through B. Then stop A while sending requests and record how long failures continue. Repeat during a deployment, with slow in-flight requests, and with B near its capacity limit. These are validation steps for an implementation, not experiments already performed.

The design now has an answer to losing one application machine: route future work to another instance with enough spare capacity. It still sends every redirect to the same database. A cache would not improve the failure mechanism we just built.

In V3, the request volume changes enough to make those database reads the next problem.
