URL Shortener V2: Survive an application-machine failure

Series navigation

This paper is V2 of the URL Shortener architecture series.

  • Previous: V1
  • Next: V3

New requirement

Temporary downtime from losing an application machine is no longer acceptable. Deploying a new application version should also avoid interrupting redirects. Traffic and storage remain at V1 levels.

Where V1 fails

In V1, the process accepting requests is the only route to the database. The data may be intact while a process crash, machine failure, or deployment makes the entire service unreachable.

Smallest revision

Run multiple application instances behind a load balancer: 

                         +----------------+
                     +-->| application 1  |--+
client -> load balancer  +----------------+  |
                     |                       +--> database
                     +-->| application 2  |--+
                         +----------------+

The instances keep no authoritative local state. A request can reach any healthy instance, and the database remains the source of truth. The load balancer stops routing to an instance that fails its health check.

Random code generation already supports multiple writers. Each instance generates candidates independently, and the database primary-key constraint resolves the unlikely case in which two instances propose the same code.

What this version buys and costs

The application tier can now survive one instance failure if the remaining instances have enough capacity. Deployments can replace instances gradually. The load balancer becomes infrastructure that must itself be redundant, and the database is still a single point of failure.

Notice that V2 did not add a cache. Redundancy in the application tier and database read capacity are different requirements.
