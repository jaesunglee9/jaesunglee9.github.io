URL Shortener V7: Record clicks without slowing redirects

New requirement

Users want click counts by link, time, and region. Counts may be delayed and occasionally approximate, but analytics must not noticeably increase redirect latency.

Where the previous design fails

Updating a counter in the mapping row for every redirect changes a read-heavy path into a write-heavy one. A popular link causes many clients to contend on the same counter, and an analytics outage can interrupt redirects.

Smallest revision

Append a click event to a log and aggregate it outside the redirect's mapping lookup: 

                         +-> cache / mapping store -> redirect
redirect application ---+
                         +-> event log -> consumers -> analytics store

An event might contain the code, timestamp, request region, and a small amount of deliberately selected metadata. Consumers aggregate events into reporting tables independently of link resolution.

At the V3 average of about 3,860 redirects per second, 200 bytes of raw event data per redirect produces: 

3,860 events/second * 200 bytes * 86,400 seconds
  = about 67 GB/day of raw events

At the 40,000-request peak, the event log must temporarily accept about 8 MB per second before its own replication and protocol overhead.

Delivery and counting semantics

If the application waits for a durable log acknowledgement, it reduces event loss but adds a dependency to the request. If it sends without waiting, redirects are less coupled to the log but events can disappear during failure. At-least-once delivery may duplicate events, so consumers need event IDs or must accept approximate counts.

These are product choices. “Exactly once” is not a free queue setting; it requires the producer, log, consumer, and analytics store to agree on how a processed event is identified and committed.

If the pipeline stops, redirects should continue while the log retains events for later processing. Retention capacity determines how long consumers may fall behind before analytics data is lost.

Abuse uses the same separation carefully

Rate limits and coarse abuse checks can happen synchronously at the edge. Expensive classification and reporting can consume the event stream asynchronously. Disabling a confirmed malicious link returns to the mapping system, where cache invalidation and cross-region propagation determine how quickly redirects stop.

V7 keeps reporting work away from the latency-sensitive lookup while making the permitted delay and loss explicit.
