URL Shortener V7: Record clicks without slowing redirects

A creator wants to know whether anyone opened the link they shared. We could increment a counter every time we redirect, but that adds a write to the operation we have spent the series making fast.

We'll send click events to a separate processing path and decide exactly what happens when that path slows down. “Asynchronous” only helps once queues, retries, and data loss have concrete rules.

Decide what the count represents

The product wants counts by link, time, and region. Results may arrive late, and occasional missing events are acceptable. Analytics must not noticeably increase redirect latency.

Here, a click event means the service handled a valid redirect request. It does not prove that a human clicked, that the browser received the response, or that the destination loaded. Bots, previews, and client retries can all produce requests. Unique visitors and fraud-adjusted counts would need separate definitions.

We preserve the explicit no-store redirect policy from V1 so compliant caches do not routinely serve repeat redirects without contacting the service. Even then, request counts remain an observation of the shortener's traffic rather than a measurement of successful page views.

Why a counter in the mapping row becomes a problem

Suppose a popular code receives ten thousand requests in one second. If each request increments the same database row before returning, they compete to update the same piece of state.

Sharding mappings does not spread that one counter across shards. The analytics write can delay the redirect, and an unavailable counter store can prevent an otherwise valid link from working.

We instead give reporting its own path: 

                           +-> cache / mapping store -> redirect response
redirect application -----+
                           +-> bounded local buffer
                                  -> event log -> consumers -> analytics store

The buffer is part of the failure model. It is not an unlimited place where writes can wait until the problem disappears.

Choose a concrete delivery policy

For this version, the request handler attempts a nonblocking enqueue after resolving a valid mapping. A background sender batches buffered events into a replicated log. The redirect does not wait for that log to acknowledge the batch.

An event can contain: 

event_id:       one stable ID for this event
code:           the resolved short code
occurred_at:    time the service handled the request
request_region: the region serving the request

The sender reuses the same event ID when retrying an uncertain append. It does not create a new ID for each delivery attempt.

We collect only the fields needed for the defined reports. Adding IP addresses or full user-agent strings has privacy and retention consequences and is unnecessary for the counts above.

There are two places where an event can be lost before reaching the log: the local buffer can be full, or the application can crash while holding unsent events. In either case, the redirect remains available and the count may be low. We record buffer drops and sender failures as operational metrics so approximate counts do not silently look exact.

This is a deliberate best-effort policy at the request boundary. If the product later requires an audit record for every accepted redirect, it must pay for a stronger acknowledgement path or change the acceptance rule.

Size the log and the recovery work

Using V3's average rate and 200 bytes of raw event data: 

3,860 events/second * 200 bytes * 86,400 seconds
  = 66,700,800,000 bytes/day
  = about 66.7 GB/day

At the peak rate: 

40,000 events/second * 200 bytes = 8 MB/second

Replication, record metadata, indexes, and protocol overhead add to those raw numbers. Three days of raw events would be roughly 200 GB; three replicated copies would be roughly 600 GB before overhead.

Storage retention tells us how long consumers may fall behind. It does not tell us how fast they catch up. For example, a one-hour consumer outage at the average rate creates: 

3,860 * 3,600 = 13,896,000 events of backlog

If consumers process 8,000 events/second after recovery:
net drain rate = 8,000 - 3,860 = 4,140 events/second
catch-up time  = 13,896,000 / 4,140 = about 56 minutes

That estimate assumes arrivals remain at the average rate and the consumer sustains the proposed capacity. Those are teaching assumptions. If consumption merely matches new arrivals, the backlog never shrinks.

A ten-second local buffer at the peak rate would hold 400,000 events, or about 80 MB of raw payload across the fleet, with additional object overhead. A long log outage will exceed it. We cap the buffer, count dropped events, and continue redirecting.

Process an event once even when delivery repeats

A sender can append an event successfully and lose the acknowledgement. Retrying may put the same event into the log again. A consumer can also process an event and crash before recording its progress.

Suppose event E increments the count, then the consumer crashes: 

1. Read E.
2. Increment the hourly counter.
3. Crash before acknowledging progress.
4. Restart and receive E again.

Simply replaying step two would double-count E. If we want to suppress these delivery duplicates, the analytics store can keep processed event IDs with a uniqueness constraint.

The consumer performs one local transaction: 

begin transaction
insert event ID into the processed-events table
if the ID was newly inserted:
    increment the aggregate for code, time bucket, and region
commit transaction
acknowledge consumer progress afterward

If the transaction fails, neither effect commits. If it commits and progress acknowledgement is lost, replay sees the existing ID and skips the increment. Inserting the ID and updating the counter in separate transactions would leave another crash window.

Deduplication storage needs its own capacity and retention policy. IDs must remain available for at least the replay window we promise to handle; replaying older events after removing their IDs can count them again.

This gives a precise guarantee for processed events within that policy. It cannot recover events dropped before the log. It also does not merge two distinct redirect requests from a client retry: those are different events under our counting definition.

Kafka's delivery-semantics documentation makes the same boundary important: writing results to an external store requires coordinating stored results with consumer progress. A log's delivery setting alone does not make every downstream effect exactly once.

Keep reporting scalable too

If we partition the event log only by short code, one very popular link can concentrate work on one partition. Our counts do not require a global order of clicks, so we can distribute events more broadly, for example by event ID.

Consumers can aggregate batches before writing results. At larger scale, they can maintain partial counters and combine them for reporting so one global row does not become the same hot counter we removed from the redirect path. Partial aggregation and duplicate handling must agree; retries must not add the same batch twice.

For hourly reports, use the event's occurrence time rather than the time a delayed consumer happens to process it. Late events can update an earlier bucket. Clock skew still limits accuracy, so the report should expose its freshness and avoid implying that the newest bucket is complete.

Walk through an analytics outage

If consumers stop while the log remains available, senders can continue appending. Alerts on the age of the oldest unprocessed event and remaining retention time tell us how close we are to losing replayable data.

If the log becomes unavailable, senders retry within bounded budgets and buffers fill. Once buffers are full, the chosen policy drops analytics events and increments drop metrics. It does not make redirect handlers wait indefinitely or consume unbounded memory.

Recovery should drain gradually. A sender retry storm and a consumer catch-up storm can overload the log and analytics store just as a cold cache can overload the mapping database.

Expensive abuse classification can consume these events separately. A confirmed disable decision goes back to the mapping and policy system, where V3's cache rules and V6's regional propagation rules determine when redirects stop. Analytics lag must not be confused with a guarantee of immediate enforcement.

What completes this design?

Before trusting the reports, inject duplicate deliveries, crash a consumer before and after its transaction commits, fill the producer buffer, and stop the log. Check both the counts and redirect latency. These are proposed implementation checks; the capacity numbers here have not been measured.

The series began with a mapping stored in one database. Each revision added a mechanism for a stated problem: another application path, cached reads, a surviving database copy, partitioned storage, regional access, and finally asynchronous reporting. Each also added a condition under which the service waits, rejects work, or loses optional data. Those conditions are part of the architecture the user experiences.
