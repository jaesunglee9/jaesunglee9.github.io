URL Shortener V1: The smallest durable shortener

A user pastes a long URL, receives a short one, and shares it. Tomorrow, the application restarts. That short link should still work. Our first design needs somewhere to keep the mapping, but it does not yet need a fleet of servers.

This is V1 of the URL Shortener architecture series. We'll follow a link from creation to redirection, then look at what happens when the database commits but the client never receives the response.

  • Previous: V0
  • Next: V2

How much work does the first version do?

We'll use these teaching assumptions:

  • One million new links per month, with no automatic expiration.
  • About ten redirects per creation in average traffic.
  • Busy periods at ten times the average request rate.
  • Mappings survive application restarts.
  • Temporary service interruption during a server failure is acceptable.

A 30-day month gives us: 

1,000,000 / (30 * 24 * 60 * 60) = 0.386 creations/second
0.386 * 10                     = 3.86 redirects/second

Busy period: about 4 creations and 40 redirects/second

Those numbers make one application server and one database a reasonable starting point. They do not prove that a particular implementation will be fast enough. We still need to measure request latency, database work, and connection use under the expected mix of requests.

Give the mapping one home

The application handles HTTP and the database owns the mappings. We'll use PostgreSQL to make the schema and transaction examples concrete. 

client -> application -> PostgreSQL
             |
             +-> HTTP redirect back to the client

The redirect is a response to the client. The application does not fetch the destination page or relay its contents. 

CREATE TABLE links (
    code       TEXT PRIMARY KEY,
    target_url TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

The primary key prevents two mappings from owning the same code. The target URL need not be unique: two intentional creation requests can produce two short links to the same destination.

For this version, a mapping is immutable once created. Link editing, expiration, and disabling will need explicit rules when we introduce caches and abuse handling.

Follow one creation

Suppose the client sends: 

POST /links
Content-Type: application/json

{"url":"https://example.com/articles/a-long-path"}

The application first parses the URL with a standard parser. Our initial policy accepts an absolute HTTP or HTTPS URL with a host and rejects embedded credentials. We also set input-size limits before storing it. Parsing checks the form of the address; it does not establish that the destination is trustworthy or will remain available.

Next, the application generates a candidate code and tries to insert it. This PostgreSQL statement uses parameters supplied by the driver: 

INSERT INTO links (code, target_url)
VALUES ($1, $2)
ON CONFLICT (code) DO NOTHING
RETURNING code;

PostgreSQL's INSERT documentation explains the two parts we need: a conflict can skip the insert, and the returning clause reports rows actually inserted. A returned code means this statement inserted a row. An empty result means another mapping already owns that code.

The request handler therefore has a small loop: 

validate the destination
repeat up to a bounded collision limit:
    generate a candidate
    begin a transaction
    attempt the insert
    if no row was inserted:
        end the transaction and try a new candidate
    otherwise:
        commit
        return the short URL only after commit succeeds
return a temporary failure if no attempt succeeds

Only a code collision belongs in that retry loop. A connection failure or a timeout is a different outcome. Retrying every database error as though it were a collision can hide an outage and produce an unbounded request.

After the commit succeeds, the service returns: 

HTTP/1.1 201 Created
Location: https://sho.rt/aB3xQ9mN2z
Content-Type: application/json

{"short_url":"https://sho.rt/aB3xQ9mN2z"}

The ordering matters. Returning the URL before committing would let a client receive a link that disappears when the application crashes. Here we assume the database uses durable commit settings and persistent storage. A database acknowledgement is only as strong as those settings and the failures the storage can withstand.

Why random codes still need a constraint

A sequence would give us unique integers. Encoding them in base 62 makes them compact, but neighboring values remain easy to enumerate.

We'll instead generate ten characters uniformly from the 62 ASCII letters and digits, using a cryptographically secure random generator. A library should sample the alphabet without modulo bias. The available space is: 

62^10 = 839,299,365,868,340,224 codes

After five years at V1's creation rate, we would have 60 million mappings. With uniform independent candidates, the chance that the next candidate is already occupied is approximately: 

60,000,000 / 62^10 = 7.15 * 10^-11

That is the probability for the next attempt, not the probability that no collision ever occurs. We do not need collisions to be impossible. If two concurrent requests choose the same candidate, the primary key admits at most one mapping; the other request generates a new candidate.

Randomness makes this rare and lets application instances generate candidates independently. The database supplies the uniqueness guarantee. Neither property makes a short URL an authorization mechanism: anyone who has a public short link can use it.

Hashing the destination would solve a different problem. Reusing one code for an identical URL introduces deduplication rules, including what to do with URL variants, different owners, and different expiration policies. We do not need those rules to satisfy the current requirements.

Follow the short link

For a request to the short path, the application runs a parameterized lookup: 

SELECT target_url FROM links WHERE code = $1;

A found row produces: 

HTTP/1.1 302 Found
Location: https://example.com/articles/a-long-path
Cache-Control: no-store

We choose a temporary redirect and explicitly ask caches not to store the response. A 302 status alone does not mean “never cache this.” The cache policy matters if later visits must reach the shortener, for example to enforce disabling or record visits. See the redirect semantics and the no-store directive.

A successful lookup with no row produces a 404. A failed lookup produces a temporary failure such as 503. We also prevent caching those responses in this design, so a temporary error is not retained as a lasting result. The application must not translate “I could not reach the database” into “this link does not exist.”

The awkward case: the commit succeeds, the response disappears

There is a gap between storing a mapping and delivering its URL: 

1. Database commits code A.
2. Application sends the success response.
3. Connection breaks before the client receives it.
4. Client retries the creation request.
5. Database commits code B for the same destination.

Both links are valid. The client simply does not know about A. This is the baseline behavior, and a timeout can leave the client uncertain even when the server reports no success.

If duplicate creation is unacceptable, the API can accept an idempotency key. Store the key, a fingerprint of the request, and the resulting mapping together under a unique constraint. A retry with the same key and input returns the original result; reusing the key for different input is rejected. With authenticated users, scope the key to the caller.

That change also needs a retention policy: forgetting a key eventually allows the same request to create another link. We defer it here because V0 permits a new mapping for each creation request.

What do we need to operate this?

Suppose a row, its metadata, and its share of the index consume 500 bytes. This is a sizing assumption, not a measurement of the schema above. 

1,000,000 links/month * 60 months * 500 bytes = 30 GB

Long URLs and database overhead can change the result substantially. We would measure representative rows and indexes, then allow room for logs, maintenance, backups, and growth.

Before relying on this design, test the failure sequences it claims to handle: restart the application after a successful creation, force a code collision, disconnect during commit, and make the database unavailable during a lookup. These are proposed checks; no benchmark or failure experiment is claimed here.

Persistent storage also needs a recovery plan. A backup and a tested restore protect against mistakes and storage loss that an application restart test does not cover. The acceptable amount of lost data and restore time must be decided before deployment.

At this stage, losing the application server still makes every link unreachable until it recovers. The mappings can be perfectly intact while the service is down. V2 addresses that specific failure.
