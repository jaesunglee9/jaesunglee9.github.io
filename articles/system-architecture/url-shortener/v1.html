URL Shortener V1: The smallest durable shortener

Series navigation

This paper is V1 of the URL Shortener architecture series.

  • Previous: V0
  • Next: V2

Requirement

The first version has modest traffic:

  • 1 million new links per month.
  • About 10 redirects for each creation request in steady traffic.
  • A busy period may reach ten times the average rate.
  • Links do not expire automatically.
  • Data must survive an application restart.
  • Temporary downtime during a machine failure is acceptable.

Using a 30-day month, the average request rates are: 

1,000,000 / (30 * 24 * 60 * 60) = 0.39 creations/second
0.39 * 10                           = 3.9 redirects/second

The approximate busy-period rates are therefore 4 creations and 40 redirects per second. One ordinary application and database can plausibly serve this workload. We should measure the implementation before assuming otherwise.

Design

The complete architecture is: 

client -> application -> database

The database contains the durable mapping: 

CREATE TABLE links (
    code       TEXT PRIMARY KEY,
    target_url TEXT NOT NULL,
    created_at TEXT NOT NULL
);

Creating a link follows this path:

  1. Parse the destination and apply the service's URL policy.
  2. Generate a candidate short code.
  3. Insert the mapping.
  4. If the primary-key constraint reports a collision, generate another code and retry.
  5. Return only after the database commits.

The application uses a standard URL parser and accepts only absolute http or https destinations with a host.

Redirection is a primary-key lookup from code to target_url. The application returns the stored destination in a Location header.

Choosing a code

A database sequence would provide unique integers. Encoding an integer in base 62 makes it shorter, but does not make neighboring values unpredictable. The sequence also makes the database the allocation point for every code.

Instead, the application can generate a ten-character base-62 code with a cryptographically secure random generator. Its namespace contains: 

62^10 = 839,299,365,868,340,224 possible codes

The database constraint, rather than probability, supplies the uniqueness guarantee. Randomness merely makes collisions uncommon and allows independent application instances to propose codes without coordinating first.

Hashing the destination is not required. A deterministic hash would introduce a global deduplication policy: the service would need to decide whether URL variants are equivalent and how different owners, expiration dates, and analytics share one code. This design gives each intentional creation its own link.

Retrying a creation

If the database commits but the response is lost, the client cannot tell whether the mapping was created. Retrying the baseline request creates another short link.

A product that requires safe retries can accept an idempotency key and store it with the mapping under a unique constraint. Repeating a request with the same key can then return the original link, while a new key represents an intentional new link. The baseline does not require this behavior, so the schema and creation flow above omit it.

Capacity

Suppose one row, its metadata, and its index overhead consume approximately 500 bytes. Five years of V1 growth require: 

1,000,000 links/month * 60 months * 500 bytes = 30 GB

This estimate should later be replaced by measurements from the actual schema. For now, it confirms that a single database is a reasonable starting point.

Failure boundary and deferred work

The application machine and database are both single points of failure. That is consistent with the V1 requirement. Caches, replicas, shards, queues, and regional deployments would add failure modes without solving a current requirement, so V1 defers them.
