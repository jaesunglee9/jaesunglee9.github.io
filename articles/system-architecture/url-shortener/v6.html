URL Shortener V6: Serve users in several regions

Series navigation

This paper is V6 of the URL Shortener architecture series.

  • Previous: V5
  • Next: V7

New requirement

Users far from the original deployment experience unacceptable network latency. Redirects should continue when an entire region is unavailable. Creation may also need to remain available from more than one region.

Where V5 fails

Sharding divides data but does not move it closer to users. A request still crosses a continent or ocean to reach the deployment, and a regional network failure can make every shard unreachable.

First option: one write region, global reads

Keep creation in one home region and replicate mappings to read stores or caches elsewhere: 

                         +-> region A: primary writes
global traffic routing -+-> region B: cache + read replica
                         +-> region C: cache + read replica

This keeps one ordering authority for creation and makes the redirect path local for most users. Its main costs are replication lag and reduced creation availability when the home region fails. The V4 rule for avoiding false 404 responses must now work across a much slower regional boundary.

Second option: create links in every region

Random codes allow regions to generate candidates without sharing a global sequence. Each region can durably accept creations and replicate mappings to the others.

This improves creation latency and regional availability, but introduces concurrent writes, collision resolution across regions, replication conflicts, and more complicated ownership of each record. A uniqueness constraint within one region is no longer a global guarantee. If two regions accept the same code for different destinations, discovering the conflict later cannot preserve both short URLs as originally returned.

The service must therefore choose a global uniqueness strategy. It can reserve codes through a shared authority, divide the code space into disjoint regional namespaces, or accept a quantified collision risk from a sufficiently large random namespace. The last choice is probabilistic rather than a correctness guarantee and must be described that way.

Choosing between them

The choice depends on the required behavior during a regional partition:

  • If globally consistent creation matters more than write availability, keep a single write authority or require cross-region agreement.
  • If regional creation availability matters more, accept asynchronous replication and define conflict behavior.
  • Redirects can usually favor availability because existing mappings rarely change, but disabling an abusive link may require faster global propagation.

Multi-region architecture is therefore a consistency and operations decision, not merely another layer of load balancers.
