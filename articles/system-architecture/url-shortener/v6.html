URL Shortener V6: Serve users in several regions

A user on another continent can wait on the network even when our database query takes almost no time. Sharding helped us fit and operate the mappings, but all those shards still live far away.

We'll move reads closer to users while keeping a clear answer to who may create a mapping. Then we'll examine what changes if every region must accept writes independently.

Decide what a region failure is allowed to interrupt

The new requirements are lower redirect latency for distant users and recovery when the primary region becomes unavailable. We continue to protect acknowledged mappings against the single failure boundary being discussed—now one region rather than one machine.

Creation is much less frequent than redirection in our workload. For this version, we accept slower creation and a temporary creation outage during a regional partition. That lets us choose one write authority per shard instead of making concurrent regional writes a baseline requirement.

Cached or locally replicated links should remain readable where a healthy copy exists. A lookup that cannot establish whether a mapping exists may return 503 during recovery. We still do not turn uncertainty into 404.

Put the frequent operation near the user

Keep shard primaries in region A. Regions B and C have application instances, caches, and read copies. Global routing sends a visitor to a healthy nearby region. 

                         +-> region A: applications + shard primaries
global traffic routing -+-> region B: applications + cache + read copies
                         +-> region C: applications + cache + read copies

Creation in B or C -> write authority in A
Replication       -> copies in B and C

The regional service uses the same bucket mapping from V5 to find the relevant shard copy. Cross-region replication adds a second dimension to routing: which shard owns the code, and which regional copy can answer this request.

For an illustrative comparison, suppose a distant round trip takes 160 milliseconds and a regional one takes 15 milliseconds. Avoiding the distant trip can save roughly 145 milliseconds on that part of a request. These are example inputs, not measured latency or a promise about a geographic pair.

The benefit depends on how many requests can finish locally. Requests for a just-created mapping may still take the slower path, so we need to inspect tail latency as well as an average.

Follow a link created in A and opened in B

Asynchronous read copies can lag: 

1. A commits code X.
2. Client receives X and sends it to a user in B.
3. B's cache misses.
4. B's read copy has not applied X yet.
5. B consults the current write authority.
6. B returns the redirect and may cache X.

This is V4's replica-miss rule crossing a much slower network. The application must budget enough time for the remote lookup or return a temporary failure when its deadline expires.

A locally found immutable mapping can be served immediately. A local absence needs an authoritative check. If the network to the authority is unavailable, B cannot distinguish “unknown code” from “known code that has not arrived here.” We choose 503 in that case.

Do not cache that failure as an absent mapping. Otherwise restoring the network might still leave the new link hidden behind a negative entry.

Replication policy determines what survives losing A

Asynchronous replication alone can leave the newest acknowledged mappings only in A. If A is lost before they reach another region, changing traffic routing does not recover them.

To keep our acknowledgement guarantee, each shard in this design requires a durable copy in a designated recovery region before creation succeeds. Assume that region is B. The local redundancy from V4 can remain, but it does not replace the cross-region copy.

This adds a distant acknowledgement to creation latency and makes creation unavailable if the required cross-region path is broken. That is the cost we accepted at the start. C can remain an asynchronous read region and therefore is not automatically an eligible recovery authority.

The distinction between a durable recovery record and a query-visible row still applies. Before serving authoritative reads after promotion, the candidate must apply the records required by its recovery policy. The PostgreSQL replication documentation provides concrete examples of acknowledgement stages, though the complete regional failover procedure is a separate system design.

Follow the loss of the primary region

Recovering the service requires more than changing a DNS record:

  1. Stop routing new user traffic to A through the selected global routing mechanism.
  2. Establish that A cannot continue writing, using the database control system's fencing and ownership rules.
  3. Recover and promote the eligible shard copies in B.
  4. Publish the new shard authorities and refresh application connections.
  5. Re-establish the required remote durable copies before resuming creation under the same policy.

Cached redirects in healthy regions can continue during parts of this sequence. Unresolved requests may fail temporarily while no safe authority is available.

Routing changes do not instantly move existing connections or invalidate every cached DNS answer. Recovery tests must include clients still trying the old path and applications holding old shard maps.

If A is merely isolated rather than destroyed, independently promoting writers on both sides would create competing authorities. We keep the single-writer policy even when that means refusing writes. Recovery ownership needs a coordination system that itself survives the intended region failure; a controller hosted only in A would leave a gap in the design.

After promotion, creation may remain unavailable while another remote copy catches up. Requiring both zero acknowledged data loss and uninterrupted writes through arbitrary partitions would be a different contract.

What if every region must create links?

Now suppose the product cannot accept that creation outage. A caller in an isolated region must receive a new working link without contacting another region.

Random codes help regions propose candidates independently, but a local unique constraint checks only local data. Two regions could both accept the same code for different destinations. Discovering the conflict later cannot make the one public path preserve both promises.

There are several possible choices:

Strategy Creation behavior
Shared global reservation Wait for the reservation authority; an isolated region may be unable to create
Disjoint regional code spaces Allocate within a region's permanently assigned space, with local collision checks
Large random space only Accept a quantified collision risk rather than a strict global guarantee

For disjoint spaces, a region identifier can be part of the otherwise opaque code. Region assignments must never overlap or be carelessly reused. A region still needs local uniqueness and replication; the prefix does not make its data durable.

This also does not make a new mapping instantly readable in another disconnected region. We would need to relax immediate global visibility, route reads to the code's origin, or wait for replication before reporting the stronger result. A uniqueness solution does not settle visibility or regional durability.

We keep the single-authority design for this series because it matches the stated priorities. The alternative is useful when the product is ready to change those priorities explicitly. The Dynamo paper is useful background on the consequences of accepting updates during failures and reconciling versions.

An immutable mapping can still need a global stop

Redirecting an old mapping is easy while its target never changes. Disabling an abusive link adds a changing piece of state.

A disable decision made in A can arrive late at caches in B and C. A short lifetime bounds some stale responses, but does not create an immediate global stop. A stricter guarantee may require a current deny-list check or refusing redirects where the required policy state is unavailable.

We therefore keep the tradeoff visible: serving a cached link during isolation favors availability; refusing it until policy freshness is established favors enforcement. The product needs to choose the acceptable delay, and every cache layer must obey it.

What would we measure?

Measure local completion rate, remote fallbacks, replication lag, creation latency, and recovery time per region. Test a new link opened remotely, an isolated write region, stale routing information, and a disable decision during partition. These are proposed checks, not measured results.

The system now has a chosen regional read path and a defined authority during recovery. V7 adds click reporting without making that latency-sensitive path wait on an analytics database.
