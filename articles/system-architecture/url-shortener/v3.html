URL Shortener V3: Redirects overwhelm the database

In V2, either application instance can resolve any short link. Adding more instances gives us more places to accept requests, but each redirect still reads the database. A popular link sends the same lookup there thousands of times.

This version introduces a cache. We'll calculate what it saves, then follow the less comfortable case where the cache disappears.

The new traffic shape

Assume the service now creates 100 million links per month. For each creation, it serves about one hundred redirects on average. Busy periods still reach ten times the average rate. 

100,000,000 / (30 * 24 * 60 * 60) = 38.6 creations/second
38.6 * 100                      = 3,860 redirects/second

Busy period: about 400 creations and 40,000 redirects/second

The database is now doing almost forty thousand primary-key reads per second at the peak. Whether that is too much depends on the database, hardware, data size, and latency target. For this revision, assume measurements show the database read path missing that target. Traffic volume alone is not proof that a cache is necessary.

The mapping is a good candidate for caching: it is small, repeatedly read, and immutable in the baseline. That gives the application something useful to reuse across requests.

Resolve through a cache

Keep the database as the durable owner of the mapping, and place a shared cache beside it: 

client -> load balancer -> application -> mapping cache
                                      |
                                      +-> database

Creation still commits to the database first. Filling the cache afterward is optional. A failed cache write must not turn a committed mapping into a failed creation.

For a redirect, the application follows this sequence:

  1. Check the cache for the short code, within a short deadline.
  2. If a mapping is present, return the redirect.
  3. Otherwise, obtain permission from the database-read budget and query the database.
  4. If a row exists, try to cache it and return the redirect even if caching fails.
  5. If the database confirms absence, return 404. If the lookup cannot complete, return 503.

A cache timeout and a cache miss both lead toward the database, but they are different operational signals. Track them separately. A rising miss rate may mean the working set changed; timeouts may mean the cache is overloaded or unreachable.

How much work does a hit save?

At the peak rate, a 95 percent hit rate leaves: 

40,000 * (1 - 0.95) = 2,000 database reads/second

That is a useful reduction only if two thousand reads, four hundred writes, and other database work fit within the latency budget. Cache hits still consume application and cache capacity.

The sensitivity matters as much as the headline number:

Cache hit rate Database reads per second
95% 2,000
90% 4,000
80% 8,000
0% 40,000

A small change in hit rate can double database traffic. Measure the request-weighted hit rate: caching many rarely used links is less helpful than keeping the links responsible for most requests.

If the frequently accessed set contains twenty million mappings and each entry needs roughly 300 bytes, the entries alone consume about 6 GB. Actual capacity also includes metadata, memory allocation overhead, spare room, and any cache replication. This is a sizing exercise; it needs measurement with representative URLs.

A cold cache can become an outage

Suppose the cache restarts empty. Forty thousand redirects now miss each second. Automatically forwarding all of them to a database sized for the normal two thousand misses would overload it.

For an illustrative budget, assume testing establishes that the database can safely admit three thousand reads per second alongside the write traffic. The application fleet should enforce that aggregate limit, with bounded concurrency and little or no waiting. Excess requests receive a temporary failure.

That means a total cache outage can reduce availability. It also keeps some traffic working and gives the system room to recover. Letting every request wait until both tiers run out of connections is worse for recovery.

The budget must apply across the fleet. Giving each of ten instances a three-thousand-read allowance does not enforce a three-thousand-read database limit. A shared limiter or conservative per-instance allocations can implement it; changing fleet size must update those allocations.

Use short cache timeouts, cap database retries, and restore cache traffic gradually. Spreading entry expiration times also avoids forcing many popular mappings to refresh together. AWS's caching guidance describes cold caches, request coalescing, and the need to test cache-unavailable behavior.

One popular code, many simultaneous misses

Even a healthy cache can miss on a newly popular link: 

100 requests for code A arrive together.
All 100 find no cache entry.
Without coordination: 100 database reads.
With local coalescing: one read per application instance,
                      with that instance's other requests waiting for its result.

The application can keep a short-lived record of the lookup already in progress for a code. Later requests on that instance share its result. The record must be removed on success, error, and timeout so a failed lookup does not block the code indefinitely.

Local coalescing does not reduce the whole fleet to one lookup. It reduces the burst to roughly one per participating instance. Start there; a distributed lock adds another failure-prone dependency and may be unnecessary.

A link can also become too hot for one cache node even when its entry never expires. A small per-instance cache spreads those reads. That introduces another copy to invalidate, so we defer it until measurements show a hot-node problem.

Missing links and changed links need different rules

A short negative-cache entry can remember that the database found no mapping. This helps when clients repeatedly request invalid codes. A timeout must never create such an entry: an unavailable database has not confirmed absence.

There is a subtle interaction with new links. A cached absence could briefly hide a subsequently created mapping. We leave negative caching disabled in this version; enabling it requires a creation/invalidation policy compatible with the immediate-read requirement in V4.

Positive entries are simpler while mappings never change. Expiration controls memory use and refresh frequency, and eviction decides which entries leave when memory fills.

If we later allow disabling links, a cache entry can outlive the database change. Consider this race: 

Reader reads the old mapping from the database.
Administrator disables the link and deletes its cache entry.
Reader finishes late and puts the old mapping back in the cache.

Deleting the entry once is therefore insufficient for an immediate-disable guarantee. Bounded lifetimes limit staleness; stricter behavior requires version-aware updates or a separate authoritative check. We must choose that behavior when disabling becomes a requirement.

How would we judge this revision?

Test the normal hit rate and the cases that break it: an empty cache, cache timeouts, a burst for one uncached code, and a distribution with more unique links. Record database admissions, rejected requests, cache latency, and end-to-end latency. The calculations above are hypotheses to validate, not benchmark results.

V3 now explains both sides of caching. Repeated reads become cheap, while cache loss becomes a capacity event we must contain. The database is still one machine, so an uncached link can fail when that machine fails. V4 gives the durable data another place to survive.
