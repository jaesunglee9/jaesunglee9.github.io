URL Shortener V3: Redirects overwhelm the database

Series navigation

This paper is V3 of the URL Shortener architecture series.

  • Previous: V2
  • Next: V4

New requirement

Usage grows to:

  • 100 million new links per month.
  • About 100 redirects for each creation request in steady traffic.
  • A busy period may reach ten times the average rate.
  • The redirect path must remain fast under that peak.

The average rates become: 

100,000,000 / (30 * 24 * 60 * 60) = 38.6 creations/second
38.6 * 100                          = 3,860 redirects/second

The busy-period targets are approximately 400 creations and 40,000 redirects per second. Reads now dominate the workload.

Where V2 fails

Adding application instances does not remove database reads. Every redirect still performs the same lookup, and popular links repeatedly request the same rows. Eventually the database's latency or read throughput misses the target.

Smallest revision

Place a distributed cache in front of the mapping database: 

client -> load balancer -> application -> mapping cache
                                      |
                                      +----------> database

The application uses the cache-aside pattern:

  1. Look up the code in the cache.
  2. On a hit, return the redirect.
  3. On a miss, read the database.
  4. Put the mapping in the cache and return the redirect.

At 40,000 peak redirects per second, a 95 percent hit rate leaves: 

40,000 * (1 - 0.95) = 2,000 database reads/second

That calculation describes the benefit more clearly than merely placing a cache box in a diagram. The hit-rate assumption must be verified against real traffic.

If the frequently accessed set contains 20 million mappings and a cache entry requires roughly 300 bytes, its raw size is about 6 GB. Actual provisioning must also allow for cache metadata, allocator overhead, replication, and growth.

New failure modes

The cache is an optimization rather than the authority. Losing it should increase database load, not lose mappings. The fallback is dangerous if the database cannot absorb a sudden wave of misses, so the service also needs timeouts, admission control, and a gradual cache warm-up strategy.

Other cases now matter:

  • An eviction policy decides which mappings remain cached.
  • A short-lived negative entry can reduce repeated lookups for unknown codes.
  • Disabled or changed links require invalidation or a bounded cache lifetime.
  • Concurrent misses for one popular code should be coalesced.
  • A very hot code may need replication across cache nodes or a small per-instance cache.

V3 improves redirect capacity and latency. It does not make the source of truth highly available.
