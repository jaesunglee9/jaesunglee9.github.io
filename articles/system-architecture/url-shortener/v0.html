URL Shortener: Problem and Architecture Roadmap

In this series, we'll design a URL shortener: a service that turns a long URL into a short link you can share. When someone opens that link, the service sends them to the original address.

This article is the introduction to the series. It defines what the service should do, what happens when a request fails, and the assumptions we'll use. It also lays out the problems we'll tackle in later versions. The first design comes in V1, starting with one application server and one database.

What happens when someone opens a short link?

The service stores a mapping from a short code to the original URL. After submitting a URL, a client receives a short link such as: 

https://sho.rt/aB3xQ9

Opening this link asks the service to look up aB3xQ9 and redirect the client to the stored URL. The client only needs the code to work; it should not depend on how the code is constructed. We'll decide how to allocate codes in V1, including whether to generate them sequentially, randomly, or another way.

Functional requirements

Create a short link

Input
An absolute destination URL.
Success
The service atomically assigns a short code and durably records its mapping to the destination. It returns the short URL only after that transaction commits.
Rejection
If the destination does not satisfy the service's URL policy, the service returns a validation error and creates no mapping.
Storage failure
If the mapping cannot be committed, the service does not report successful creation.

The HTTP interface may take this form: 

POST /links
Content-Type: application/json

{"url":"https://example.com/articles/a-long-path"}

A successful response uses 201 Created and identifies the new resource: 

HTTP/1.1 201 Created
Location: https://sho.rt/aB3xQ9
Content-Type: application/json

{"short_url":"https://sho.rt/aB3xQ9"}

If the destination is not acceptable, the service rejects the request before opening the creation transaction: 

HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"invalid_destination_url"}

No code or mapping is created in this case.

If the service knows that durable storage is unavailable and cannot commit the mapping, it reports temporary unavailability rather than returning a short URL: 

HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json

{"error":"link_storage_unavailable"}

Follow a short link

Input
A short code in the request path.
Success
For a known code, the service returns a redirect whose Location header contains the stored destination.
Unknown code
If no mapping exists, the service returns 404 Not Found.
Storage failure
If the service cannot determine whether a mapping exists, it reports temporary unavailability rather than claiming that the code is unknown.

The client follows a short link with a request such as: 

GET /aB3xQ9
Host: sho.rt

For a known code, the response contains the stored destination: 

HTTP/1.1 302 Found
Location: https://example.com/articles/a-long-path

For a code with no mapping, the service returns: 

HTTP/1.1 404 Not Found
Content-Type: application/json

{"error":"short_link_not_found"}

If storage is unavailable and the service cannot complete the lookup, it returns a distinct failure: 

HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json

{"error":"link_lookup_unavailable"}

Returning 404 for this last case would make a temporary infrastructure failure behave identically with the case where the mapping does not exist.

302 Found is a temporary redirect, but does not by itself prevent caching. V1 will set an explicit cache policy so later visits reach the shortener. A permanent redirect is a separate product choice for immutable links that clients may cache.

Baseline assumptions

  • Each creation request creates a new short link, even when another link has the same destination.
  • Destinations must be absolute HTTP or HTTPS URLs.
  • Links do not expire or change in the baseline.
  • The service redirects to destinations; it does not fetch their contents.

Variable requirements

The papers vary five dimensions while keeping the functional contract recognizable:

  • Request volume and the ratio of redirects to creations.
  • Accumulated mappings and storage requirements.
  • Machine, database, and regional failure tolerance.
  • Consistency required immediately after creation or disabling a link.
  • Work that may happen asynchronously, such as analytics.

A larger value in one dimension does not automatically require every later component. For example, application redundancy does not by itself justify a cache, and partitioning does not provide replication.

Roadmap

We'll grow the design one version at a time. Each article adds a requirement, shows where the previous design falls short, and introduces the smallest change that addresses it. The numbers used along the way are teaching assumptions, not measurements of an existing service.

The table below shows what changes at each step and why.

Paper New requirement Limitation exposed Architectural change
V1 Persist modest traffic Memory is lost on restart One application and one database
V2 Survive an application-machine failure One process is the only request path Load balancer and stateless instances
V3 Serve much heavier redirect traffic Every redirect reaches the database Distributed mapping cache
V4 Survive a database-machine failure Cache is not durable storage Replication and failover
V5 Exceed one database's operational capacity Replicas copy rather than divide data Partitioned mapping store
V6 Reduce distant-user latency and regional risk One deployment is far away and one regional failure domain Regional reads and global routing
V7 Record clicks without delaying redirects Synchronous counters turn reads into writes Asynchronous event pipeline

We'll use the same problem-solving approach throughout the series.

  1. State the new requirement and quantify it where useful.
  2. Trace the relevant operation through the previous architecture.
  3. Identify the exact resource, guarantee, or failure boundary that no longer satisfies the requirement.
  4. Add the smallest useful mechanism.
  5. Recalculate capacity or latency at the changed boundary.
  6. Describe the new failure modes and operational cost.
  7. Leave unrelated concerns for a later version.

This keeps the comparison causal. The reader can see both what a component buys and what complexity arrives with it.
