URL Shortener V5: The mapping set reaches billions of links

New requirement

V3's creation rate continues for five years, and links still do not expire: 

100,000,000 links/month * 60 months = 6,000,000,000 mappings
6,000,000,000 * 500 bytes          = 3 TB logical data

With three copies, the mapping store alone requires roughly 9 TB before backups and additional operational headroom. Index maintenance, backup time, restore time, and re-replication may become unacceptable before raw disk space runs out.

Where V4 fails

A larger primary can postpone the problem, and that may be the correct response. Eventually, however, one database's storage, write throughput, or recovery time crosses its operational limit. Read replicas copy the whole data set; they do not divide it.

Smallest revision

Partition mappings by a hash of the short code: 

                          +-> shard 1 -> replicas
application -> router ---+-> shard 2 -> replicas
                          +-> shard 3 -> replicas
                          +-> ...

Every code maps to exactly one primary shard, and its replicas hold redundant copies. A lookup and an insertion use the same routing rule. Because generated codes are random, a suitable partition function distributes new mappings broadly rather than concentrating them in one increasing key range.

If the operational target is no more than 300 GB of logical data per primary shard, 3 TB requires at least ten shards: 

3 TB / 300 GB = 10 primary shards

Provisioning twelve would leave some growth and rebalancing room, but the real choice must also include request throughput and the capacity needed while a machine is unavailable.

Rebalancing the data

A rule such as hash(code) mod shard_count assigns keys evenly at a fixed shard count. Increasing the count changes the result for many existing keys, which forces a large migration.

A routing table, virtual partitions, or consistent hashing can separate logical partitions from physical machines and reduce the data moved during a capacity change. The router and its configuration then become critical infrastructure. Configuration versions must be rolled out safely so that old and new application instances do not disagree about where a mapping lives.

Partitioning supplies capacity; replication supplies redundancy. A shard with no replica is still unavailable when its machine fails.

Cost of this version

Cross-shard backups, rebalancing, schema changes, and recovery are harder than their single-database equivalents. The service should adopt V5 only when measurements show that vertical growth, caching, and replication no longer meet storage, throughput, or recovery requirements.
