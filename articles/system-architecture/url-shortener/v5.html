URL Shortener V5: The mapping set reaches billions of links

Replication gave us another copy of the mappings. It did not make the original copy smaller. Every replica still has to store, index, and recover the full data set.

In this version, we'll split the mappings across database groups. The important question is how a request finds its owner—and how that answer changes while data moves.

The limit is operational, not just disk space

Keep V3's creation rate for five years, with no automatic expiration: 

100,000,000 links/month * 60 months = 6,000,000,000 mappings
6,000,000,000 * 500 bytes          = 3 TB logical data

The 500-byte estimate includes the assumed row and index overhead from V1. Two durable copies would use roughly 6 TB under that model. With an additional full read replica, three copies use roughly 9 TB. Backups, recovery logs, and operating headroom are extra.

Three terabytes is not a universal sharding threshold. A larger machine may be the cheapest way to keep the design simple. The reason to split the database is a measured limit: write throughput, maintenance time, restore time, or storage growth that one primary can no longer handle acceptably.

We'll assume the operational target is at most 300 GB of logical data per primary. That gives a lower bound: 

3 TB / 300 GB = 10 primary shards

Choosing twelve primary shards would leave some room for growth and movement. The actual choice also depends on request distribution and failure capacity. None of these numbers is a benchmark result.

Each mapping has one owning shard

A shard stores a subset of the mappings. Its standby stores another copy of that same subset, using the durability and failover policy from V4. 

                            +-> shard group 1: primary + standby
application -> routing map -+-> shard group 2: primary + standby
                            +-> shard group 3: primary + standby
                            +-> ...

The cache lookup can still use the short code directly. On a cache miss, the application routes the database request to the group that owns that code.

Creation follows the same route: generate a candidate code, determine its owning shard, and attempt the insert there. If the primary-key constraint reports a collision, generate another candidate and route that one.

This still enforces code uniqueness without checking every shard. Identical codes always select the same logical partition and therefore the same active owner. The argument depends on all writers agreeing on the partition function and ownership; inconsistent routing can break it.

Hash the short code, not the destination URL. Two intentional creations for the same destination should remain independent, as they were in V1.

Why not take the hash modulo the server count?

A direct rule is easy to write: 

owner = hash(code) mod number_of_shards

It also changes many owners when we add a shard. For a small arithmetic example, consider a code whose hash value is eight: 

8 mod 3 = 2
8 mod 4 = 0

After adding a fourth shard, the same lookup goes somewhere else. Unless the data has moved too, a valid code appears missing. Recomputing the owner is only one part of a migration.

We'll separate a stable logical partition from its current physical owner. For this teaching design, use a fixed set of 1,024 buckets: 

bucket = hash(code) mod 1024

Routing map, epoch 17:
bucket 37 -> shard group 2
bucket 38 -> shard group 5

Routing map, epoch 18:
bucket 37 -> shard group 12
bucket 38 -> shard group 5

Adding a shard changes selected routing-map entries. The bucket calculation stays the same. We choose the hash algorithm and byte encoding once and treat them as part of the storage format.

The fixed bucket count is itself a choice with a future limit. Changing it later requires another migration plan. Virtual partitions and consistent hashing offer related ways to avoid tying every key directly to the current machine count; the Dynamo paper describes virtual nodes in a production storage design.

Move one bucket without losing its writes

Suppose we want to move bucket 37 from group 2 to group 12. Group 2 must remain responsible while its data is being copied. Otherwise a creation can arrive between the copy and the ownership switch and disappear from the destination.

A teaching migration protocol can use these steps:

  1. Record the migration and its starting log position. Group 2 remains the only writer.
  2. Copy a consistent snapshot of the bucket into group 12.
  3. Stream changes after the snapshot until the destination is almost caught up.
  4. Pause writes to this bucket and drain in-flight writes. The source continues to hold ownership.
  5. Apply the final changes and durably replicate them at the destination.
  6. Fence writes at the old owner, publish the new ownership epoch, and allow the new owner to serve the bucket.
  7. Keep the old copy until stale routes and in-flight reads have been handled and the migration is verified.

Reads may briefly retry during the ownership switch, and writes to this bucket can receive a temporary failure. This design deliberately permits that bounded pause instead of requiring two writable owners.

Requests carry the routing epoch. A server that no longer owns the bucket rejects or redirects a stale request so the application can refresh its map. It must not return “no row” as though a stale route were an authoritative lookup. If it cannot establish current ownership, it returns a temporary failure.

The ownership transition needs a consistent metadata store and enforcement at the database access boundary. A local configuration reload alone cannot fence an old writer. This protocol explains the required behavior; it is not a complete migration implementation. MongoDB's range-migration procedure is a concrete example of copying data, catching up changes, updating ownership metadata, and cleaning up afterward.

What if the migration fails halfway?

Before the ownership switch, group 2 remains authoritative. We can discard or resume the incomplete destination copy.

After the switch, group 12 is authoritative. We cannot roll back by simply pointing the router at the old copy, because new writes may already exist only on group 12. Moving back is another coordinated migration.

The migration record must survive process restarts and identify whether ownership changed. Data movement also consumes disk, network, and replication capacity. Limit concurrent moves so rebalancing does not overwhelm the same shards that are serving requests.

If the metadata service is temporarily unavailable, applications can use a known map only while the ownership protocol still makes that safe. Ownership changes should stop until coordination recovers. Blindly allowing new moves while routers cannot learn about them creates conflicting views.

Data balance and traffic balance are different

Random codes and a suitable hash should spread new mappings across buckets. That balances storage reasonably well under the assumptions, but one famous link can still create most of the traffic.

Splitting other buckets will not divide requests for that single code. V3's cache and hot-key handling remain relevant. We therefore watch storage size, request rate, and latency per shard, not just total cluster utilization.

Backups also become a collection of related artifacts: shard data, recovery positions, the routing map, and in-progress migration state. A restore must reconstruct ownership as well as rows. Immutable, independent mappings make this easier than transactions spanning several shards, but restoration still needs a test.

What has V5 actually added?

We would validate this design by inserting and reading codes through different application instances, moving a bucket under traffic, restarting the migration controller, and deliberately using an old routing epoch. Every acknowledged mapping should remain reachable through its current owner, and stale routes should never create false 404s.

The service can now grow storage and write capacity by adding shard groups. Each group still needs replication to survive a machine failure. The whole deployment remains in one region, so distant users still cross the same long network path. V6 changes that geographic boundary.
