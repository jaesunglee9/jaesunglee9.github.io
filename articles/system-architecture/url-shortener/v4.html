URL Shortener V4: Survive a database failure

Series navigation

This paper is V4 of the URL Shortener architecture series.

  • Previous: V3
  • Next: V5

New requirement

Redirects must continue when a database machine fails. A link must also work as soon as the service reports that its creation succeeded.

Where V3 fails

A warm cache may hide a database outage for popular links, but uncached links still fail. The only database machine also remains necessary for every creation. A cache is not a durable replica.

Smallest revision

Use a primary database and read replicas: 

                                  +-> read replica 1
application -> cache or database +-> read replica 2
                                  +-> primary

Creation commits on the primary. Cache misses can use replicas, and a failed replica can be removed from the read pool. If the primary fails, an eligible replica can be promoted according to the database's failover procedure.

Replication changes consistency

With asynchronous replication, the following execution is possible: 

t0  primary commits code aB3xQ9
t1  service returns the new short URL
t2  client requests aB3xQ9
t3  a lagging replica does not contain aB3xQ9 and returns no row

Returning 404 at t3 would violate the new requirement. Populating the cache after the database commit improves the common case, but does not guarantee visibility: the cache write can fail or the entry can be evicted.

Two stronger policies are available:

  • On a replica miss, query the primary before returning 404.
  • Replicate synchronously before acknowledging creation.

Primary fallback keeps ordinary writes fast but sends unknown codes and recent codes to the primary. Synchronous replication provides a stronger storage guarantee at the cost of write latency and write availability when replicas cannot acknowledge. The design must choose explicitly between those costs.

Failover is a capacity question

Replication helps only if the remaining machines can serve the redirected load. Health checks, promotion rules, connection rerouting, and capacity reserved for failure must be tested together. Recovery point and recovery time objectives should state how much committed data may be lost and how long creation or redirection may be unavailable.

V4 makes storage-machine failure survivable, while adding replication lag and failover as behaviors the service must manage.
