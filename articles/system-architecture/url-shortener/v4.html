URL Shortener V4: Survive a database failure

A warm cache can make a database outage look harmless. Popular links continue to redirect while a newly created or rarely used link fails. Creation stops too, because the database is still the only place that can commit a mapping.

We'll add a durable copy and define which copy may take over. Then we'll follow a link created just before the primary fails—the case that determines whether replication actually meets our requirement.

Make the failure requirement precise

We want to survive one database-machine failure without losing acknowledged mappings. A newly created link must be readable after its successful creation response.

There can be a brief interval while the system detects failure and promotes a replacement. During that interval, unresolved requests may receive 503. We do not claim uninterrupted success for every request, or survival after every copy of the data is destroyed.

For this design, the recovery point objective is zero acknowledged mapping loss under the single-machine failure assumption. The recovery time objective needs a concrete deployment target and a measured failover procedure. We will describe the work inside that interval instead of inventing a recovery-time result.

Start with a primary and a designated standby

Keep the V3 cache and application tier. Put the primary and its standby on separate machines and storage: 

application -> cache
      |
      +-> primary P === synchronous durable copy ===> standby S
      |
      +-> optional asynchronous read replica R

P accepts creation transactions. S is the designated failover candidate. R is optional read capacity and is not automatically eligible to replace P.

Our commit policy requires the transaction's recovery records to reach durable storage on both P and S before creation succeeds. We keep that rule explicit because “there is a replica” says nothing about which acknowledged writes it has.

If S is unavailable, P can still serve reads, but creation cannot satisfy this policy. We return a temporary failure rather than silently weakening durability. A production system that must keep accepting writes after losing either machine needs additional replicas and a suitable acknowledgement and promotion policy.

Stored on a replica is not necessarily visible to a query

Replication has several stages: sending a change, receiving it, making its recovery record durable, and applying it so queries can see the row.

PostgreSQL distinguishes these stages in its synchronous replication settings. Waiting for a durable standby copy does not by itself ensure that a query on any read replica sees the transaction. Waiting for remote application can provide visibility on the selected synchronous standby, but it says nothing about an unrelated lagging replica.

Here is the problem with reading R immediately after creation: 

t0  P and S durably record code A.
t1  Service returns A to the client.
t2  Client opens A; the cache has no entry.
t3  R has not replayed A and returns no row.

A 404 at this point would falsely tell the client that its acknowledged link does not exist. Filling the cache during creation improves the common case, but a failed cache write or eviction brings the same problem back.

Choose a read rule that preserves the contract

For immutable mappings, a found row on R is usable. An absent row is inconclusive until we consult the current primary.

Our lookup policy is:

  1. Use the cache if it contains a mapping.
  2. On a cache miss, query a healthy read replica, if configured.
  3. If the replica has no row or cannot complete the query, try the current primary within the remaining request deadline and read budget.
  4. Return 404 only after an authoritative lookup confirms absence.
  5. Return 503 if the service cannot establish the result.

Without R, step two simply goes straight to the primary. V3's admission limits still apply; replication does not make an unlimited fallback safe.

This policy preserves immediate reads while P is available. It also keeps negative caching disabled, since a cached absence could bypass the authoritative check. Unknown codes and recently created codes put more load on P, so their rate belongs in capacity planning.

After failover, S becomes the authoritative primary only after replaying the required recovery records. We route authoritative reads there. A random replica with less data is not an equivalent replacement.

Follow a primary failure

Suppose P dies immediately after the client receives code A. 

1. The creation response proves P and S durably recorded A.
2. Failure detection declares P unavailable.
3. The failover controller prevents P from accepting further writes.
4. S replays the required records and is promoted.
5. Applications refresh the primary endpoint and their connections.
6. An authoritative lookup on S finds A.

Step three is fencing: making sure the old primary cannot continue acting as a writer. A machine can appear dead because the network is partitioned and later return. Promoting S while P still accepts writes can create two competing histories.

The PostgreSQL failover documentation discusses this old-primary problem and the need for external failure detection and coordination. We rely on a tested database failover controller and its fencing mechanism here; application instances do not independently elect their own preferred primary.

If the controller cannot establish that promotion is safe, writes remain unavailable. This sacrifices availability in an uncertain partition to preserve the single-writer rule.

A creation already in progress when P fails may have committed without delivering a response. That is still the ambiguous result from V1. Failover does not remove the need for idempotency when the product requires safe creation retries.

What happens after promotion?

S now serves the workload that P previously handled. It needs enough CPU, I/O, connections, and memory to do so while applications reconnect and caches refill.

For example, if the normal cache leaves two thousand database reads per second and four hundred writes, promotion must account for that mix—not just the standby's previous replay workload. Reconnection bursts and retry amplification can create a higher short-term load. Keep the admission controls while recovering.

The old P must rejoin as a replica after its state is reconciled with the new primary. Merely restarting it with its old configuration is unsafe. A replacement standby must catch up before we can restore the original two-copy acknowledgement policy and resume creation under it.

We should also distinguish a replica from a backup. Replication can quickly reproduce an accidental deletion or bad update. Backups with a tested recovery procedure address a different failure history.

Check the guarantee at its weakest point

A useful failover test records every creation response the client actually received, kills P, promotes S through the real controller, and checks every acknowledged code. It also tracks requests that never received a response separately; they may or may not have committed.

Then test the cases that challenge the policy: a lagging read replica, loss of S, an isolated P that is still running, and promotion under peak admitted load. These are proposed tests, not results from this repository.

V4 gives each acknowledged mapping a defined surviving copy and explains how that copy becomes authoritative. It has not divided the data: P, S, and R still store the same mapping set. V5 addresses the point where storing and operating that whole set on one primary is the next limit.
