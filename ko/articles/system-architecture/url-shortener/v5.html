URL 단축 서비스 V5: 매핑이 수십억 개로 늘어날 때

복제로 매핑 사본을 하나 더 만들었지만, 원래 사본의 크기는 줄지 않았습니다. 각 복제본은 여전히 전체 데이터를 저장하고 인덱스를 만들며 복구해야 합니다.

이번에는 매핑을 여러 데이터베이스 그룹에 나눠 저장합니다. 요청이 담당 그룹을 찾는 방법과 데이터를 옮기는 동안 담당 그룹이 바뀌는 과정을 살펴보겠습니다.

  • 시리즈: URL 단축 서비스 아키텍처 시리즈
  • 이전: V4
  • 다음: V6

디스크 용량뿐 아니라 운영 한계도 고려하기

자동 만료 없이 V3의 생성 속도를 5년간 유지한다고 가정합니다. 

100,000,000 links/month * 60 months = 6,000,000,000 mappings
6,000,000,000 * 500 bytes          = 3 TB logical data

매핑당 500바이트에는 V1에서 가정한 행과 인덱스의 부가 공간이 포함됩니다. 이 계산대로라면 장애 후에도 데이터를 보존하는 사본 두 개에 약 6 TB가 필요합니다. 전체 데이터를 담은 읽기 복제본을 하나 더 두면 사본 세 개에 약 9 TB가 필요합니다. 백업, 복구 로그, 운영에 필요한 여유 공간은 별도입니다.

3 TB가 모든 시스템에 적용되는 샤딩 기준은 아닙니다. 더 큰 서버를 쓰는 것이 설계를 단순하게 유지하는 가장 저렴한 방법일 수도 있습니다. 데이터베이스를 나눌지는 실제로 측정한 한계를 보고 결정해야 합니다. 쓰기 처리량, 유지보수 시간, 복원 시간, 저장량 증가를 주 서버 하나가 더 이상 허용 가능한 수준으로 감당하지 못할 때 나눕니다.

여기서는 주 서버당 논리 데이터를 300 GB 이하로 유지하는 것을 운영 목표로 가정합니다. 그러면 필요한 최소 샤드 수는 다음과 같습니다. 

3 TB / 300 GB = 10 primary shards

샤드를 12개로 잡으면 데이터 증가와 이동에 쓸 여유가 생깁니다. 실제 개수는 요청 분포와 장애 시 필요한 처리 여력에도 달려 있습니다. 이 수치들은 벤치마크 결과가 아닙니다.

매핑마다 담당 샤드 하나 지정하기

샤드는 전체 매핑 중 일부를 저장합니다. 대기 서버는 같은 매핑의 사본을 보관하며, V4의 지속성(durability) 보장과 장애 조치 정책을 따릅니다. 

                            +-> shard group 1: primary + standby
application -> routing map -+-> shard group 2: primary + standby
                            +-> shard group 3: primary + standby
                            +-> ...

캐시는 이전처럼 단축 코드로 바로 조회할 수 있습니다. 캐시에 없으면 애플리케이션이 해당 코드를 담당하는 그룹으로 데이터베이스 요청을 보냅니다.

매핑을 생성할 때도 같은 경로를 따릅니다. 애플리케이션은 후보 코드를 만들고 담당 샤드를 찾은 뒤 그곳에 삽입을 시도합니다. 기본 키 제약 조건으로 충돌이 확인되면 새 후보를 만들고 그 코드의 담당 샤드로 요청을 보냅니다.

이 방식이면 모든 샤드를 확인하지 않아도 코드의 유일성을 보장할 수 있습니다. 같은 코드는 항상 같은 논리 파티션에 속하므로 현재 담당 그룹도 같습니다. 다만 모든 쓰기 주체가 같은 파티션 함수와 담당 정보를 사용해야 합니다. 라우팅이 서로 다르면 이 보장이 깨질 수 있습니다.

해시는 원본 URL이 아니라 단축 코드로 계산합니다. V1에서처럼 같은 원본 URL에 대해 의도적으로 두 번 생성한 매핑은 서로 독립적으로 유지해야 합니다.

해시값을 샤드 수로 나눈 나머지를 쓰면?

다음 규칙은 간단합니다. 

owner = hash(code) mod number_of_shards

하지만 샤드를 추가하면 많은 코드의 담당 샤드가 바뀝니다. 해시값이 8인 코드로 계산해 보겠습니다. 

8 mod 3 = 2
8 mod 4 = 0

네 번째 샤드를 추가하면 같은 코드의 조회 요청이 다른 곳으로 갑니다. 데이터도 함께 옮기지 않았다면 유효한 코드가 없는 것처럼 보입니다. 담당 샤드를 다시 계산하는 것은 마이그레이션의 일부일 뿐입니다.

고정된 논리 파티션과 이를 현재 담당하는 물리적 그룹을 분리하겠습니다. 이 설명용 설계에서는 버킷을 1,024개로 고정합니다. 

bucket = hash(code) mod 1024

Routing map, epoch 17:
bucket 37 -> shard group 2
bucket 38 -> shard group 5

Routing map, epoch 18:
bucket 37 -> shard group 12
bucket 38 -> shard group 5

샤드를 추가할 때는 라우팅 맵에서 일부 항목만 바꾸고 버킷 계산은 그대로 유지합니다. 해시 알고리즘과 바이트 인코딩은 처음에 정하고 저장 형식의 일부로 취급합니다.

버킷 수를 고정하는 선택에도 한계가 있습니다. 나중에 개수를 바꾸려면 별도의 마이그레이션 계획이 필요합니다. 가상 파티션과 일관 해싱(consistent hashing)도 각 키의 위치를 현재 서버 수에 직접 의존하지 않게 하는 관련 기법입니다. Dynamo 논문에서는 실제 운영용 저장소 설계에 가상 노드를 사용한 방식을 설명합니다.

쓰기를 잃지 않고 버킷 옮기기

버킷 37을 그룹 2에서 그룹 12로 옮긴다고 가정합니다. 데이터를 복사하는 동안에는 그룹 2가 계속 버킷을 담당해야 합니다. 그렇지 않으면 복사와 담당 그룹 전환 사이에 들어온 생성 요청의 데이터가 이동 대상에 반영되지 않을 수 있습니다.

설명용 마이그레이션 프로토콜은 다음 순서로 구성할 수 있습니다.

  1. 마이그레이션과 시작 로그 위치를 기록합니다. 쓰기는 계속 그룹 2에서만 처리합니다.
  2. 버킷의 일관된 스냅샷을 그룹 12로 복사합니다.
  3. 스냅샷 이후의 변경 사항을 계속 전달해 이동 대상이 거의 따라잡도록 합니다.
  4. 이 버킷의 쓰기를 멈추고 진행 중인 쓰기가 끝날 때까지 기다립니다. 버킷은 계속 원본 그룹이 담당합니다.
  5. 마지막 변경 사항을 적용하고 이동 대상에서 장애 후에도 보존되도록 복제합니다.
  6. 기존 담당 그룹의 쓰기를 차단하고 새 담당 정보를 담은 라우팅 맵 버전(에포크)을 배포한 뒤, 새 그룹이 버킷의 요청을 처리하게 합니다.
  7. 오래된 경로로 오는 요청과 진행 중인 읽기를 처리하고 마이그레이션을 검증할 때까지 기존 사본을 유지합니다.

담당 그룹을 전환하는 동안 읽기 요청은 잠시 재시도가 필요할 수 있고, 이 버킷으로 보낸 쓰기 요청은 일시적인 실패 응답을 받을 수 있습니다. 이 설계에서는 두 그룹이 동시에 쓰기를 처리하도록 요구하는 대신, 제한된 시간 동안 쓰기를 멈추는 것을 의도적으로 허용합니다.

요청에는 라우팅 에포크를 담습니다. 더 이상 버킷을 담당하지 않는 서버는 오래된 라우팅 정보로 들어온 요청을 거부하거나 새 담당 그룹으로 안내합니다. 애플리케이션은 이 응답을 받고 맵을 갱신할 수 있습니다. 서버는 오래된 경로로 들어온 요청에 “행이 없음”을 반환해, 올바른 담당 그룹에서 조회한 결과처럼 보이게 해서는 안 됩니다. 현재 담당 그룹을 확인할 수 없으면 일시적인 실패를 반환합니다.

담당 그룹을 전환하려면 일관성을 보장하는 메타데이터 저장소가 필요합니다. 데이터베이스에 접근하는 지점에서도 담당 그룹만 쓰기를 처리하도록 강제해야 합니다. 로컬 설정을 다시 읽는 것만으로는 기존 쓰기 주체를 차단할 수 없습니다. 이 프로토콜은 필요한 동작을 설명한 것으로, 완전한 마이그레이션 구현은 아닙니다. MongoDB의 범위 마이그레이션 절차는 데이터 복사, 변경 사항 반영, 담당 메타데이터 갱신, 이후 정리를 보여 주는 구체적인 사례입니다.

옮기는 도중 실패하면?

담당 그룹을 전환하기 전에는 그룹 2를 기준으로 삼습니다. 이동 대상의 미완성 사본은 버리거나 복사를 재개할 수 있습니다.

전환 후에는 그룹 12를 기준으로 삼습니다. 새 쓰기가 이미 그룹 12에만 반영됐을 수 있으므로, 라우터를 기존 사본으로 돌리는 것만으로 되돌릴 수는 없습니다. 다시 옮기려면 또 한 번 마이그레이션 절차를 조율해야 합니다.

마이그레이션 기록은 프로세스를 재시작해도 남아 있어야 하며, 담당 그룹이 바뀌었는지 확인할 수 있어야 합니다. 데이터 이동에도 디스크, 네트워크, 복제 처리 여력이 필요합니다. 데이터 재분배가 요청을 처리 중인 샤드에 과도한 부하를 주지 않도록 동시에 진행하는 이동 수를 제한합니다.

메타데이터 서비스를 잠시 사용할 수 없을 때는 담당 그룹 전환 프로토콜상 안전한 동안에만 애플리케이션이 기존 맵을 사용할 수 있습니다. 담당 그룹 변경은 조율 기능이 복구될 때까지 멈춰야 합니다. 라우터가 변경을 알 수 없는데도 새 이동을 허용하면 담당 그룹에 대한 정보가 서로 달라집니다.

데이터 분산과 트래픽 분산은 별개

무작위 코드와 적절한 해시를 사용하면 새 매핑이 버킷에 고르게 분산될 것으로 기대합니다. 이 가정 아래에서는 저장량이 비교적 균등해지지만, 유명한 링크 하나에 트래픽 대부분이 몰릴 수 있습니다.

다른 버킷을 나눠도 그 코드 하나로 들어오는 요청은 나뉘지 않습니다. V3의 캐시와 요청이 몰리는 단축 코드 처리 방식은 여전히 필요합니다. 따라서 클러스터 전체 사용률뿐 아니라 샤드별 저장량, 요청률, 지연 시간도 살펴봅니다.

백업도 서로 연관된 여러 항목으로 구성됩니다. 샤드 데이터, 복구 위치, 라우팅 맵, 진행 중인 마이그레이션 상태를 함께 보관해야 합니다. 복원할 때는 행뿐 아니라 어느 그룹이 어떤 데이터를 담당하는지도 재구성해야 합니다. 매핑이 변경되지 않고 서로 독립적이어서 여러 샤드에 걸친 트랜잭션보다 복원이 쉽지만, 그래도 복원 테스트는 필요합니다.

V5에서 달라진 점

이 설계를 검증할 때는 서로 다른 애플리케이션 인스턴스를 통해 코드를 저장하고 읽어 보겠습니다. 트래픽이 들어오는 동안 버킷을 옮기고, 마이그레이션 컨트롤러를 재시작하며, 의도적으로 오래된 라우팅 에포크도 사용해 보겠습니다. 저장 성공을 응답한 모든 매핑은 현재 담당 그룹을 통해 계속 조회할 수 있어야 합니다. 오래된 라우팅 정보 때문에 잘못된 404가 발생해서도 안 됩니다.

이 설계에서는 샤드 그룹을 추가해 저장 용량과 쓰기 처리량을 늘릴 수 있습니다. 서버 장애 후에도 데이터를 보존하려면 각 그룹에 여전히 복제가 필요합니다. 전체 시스템은 아직 한 리전에 있으므로 먼 곳의 사용자는 같은 긴 네트워크 경로를 거쳐야 합니다. V6에서는 이 지리적 경계를 바꿉니다.
