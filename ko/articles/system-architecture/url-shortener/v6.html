URL 단축 서비스 V6: 여러 리전에서 사용자 요청 처리하기

시리즈 안내

이 글은 URL 단축 서비스 아키텍처 시리즈의 V6입니다.

  • 이전: V5
  • 다음: V7

새 요구사항

기존 배포 리전에서 멀리 떨어진 사용자는 허용하기 어려울 만큼 긴 네트워크 지연을 겪습니다. 리전 전체를 사용할 수 없어도 리디렉션은 계속되어야 합니다. 단축 URL 생성도 둘 이상의 리전에서 계속 가능해야 할 수 있습니다.

V5의 한계

샤딩은 데이터를 나누지만 사용자 가까이로 옮기지는 않습니다. 사용자의 요청은 여전히 대륙이나 바다를 건너 배포 리전에 도달해야 합니다. 리전의 네트워크에 장애가 나면 모든 샤드에 접근하지 못할 수 있습니다.

첫 번째 방식: 한 리전에서 생성하고 전 세계에서 조회하기

단축 URL 생성은 하나의 주 리전에서 처리하고, 매핑은 다른 리전의 조회용 저장소나 캐시로 복제합니다. 

                         +-> region A: primary writes
global traffic routing -+-> region B: cache + read replica
                         +-> region C: cache + read replica

이렇게 하면 한 곳에서 생성 순서를 정하면서 대부분의 사용자에게는 가까운 리전에서 리디렉션 응답을 보낼 수 있습니다. 대신 복제 지연이 생기고, 주 리전에 장애가 나면 단축 URL 생성 가용성이 떨어집니다. V4에서 잘못된 404 응답을 피하기 위해 세운 규칙도 이제는 훨씬 느린 리전 간 통신에서도 작동해야 합니다.

두 번째 방식: 모든 리전에서 생성하기

무작위 코드를 쓰면 전역 시퀀스를 공유하지 않고도 각 리전에서 후보 코드를 만들 수 있습니다. 각 리전은 생성 요청을 받아 매핑을 장애 후에도 보존되도록 저장하고, 다른 리전으로 복제할 수 있습니다.

이 방식은 생성 지연을 줄이고 리전별 가용성을 높입니다. 하지만 여러 리전에서 동시에 쓰기가 일어나며, 리전 간 코드 충돌과 복제 충돌을 해결해야 합니다. 각 레코드를 어느 리전이 책임질지 정하는 일도 더 복잡해집니다. 한 리전의 고유성 제약만으로는 전역 고유성을 보장할 수 없습니다. 두 리전이 같은 코드를 서로 다른 원본 URL에 할당하고 생성 성공을 응답할 수도 있습니다. 나중에 충돌을 발견해도 두 단축 URL을 각각 처음 지정한 원본 URL로 연결할 수는 없습니다.

따라서 전역 고유성을 어떻게 확보할지 정해야 합니다. 공통으로 코드를 예약하는 곳을 두거나, 코드 공간을 리전별로 겹치지 않게 나눌 수 있습니다. 충분히 큰 무작위 코드 공간을 사용하고, 충돌 위험을 수치로 평가해 받아들이는 방법도 있습니다. 마지막 방법은 정확성을 보장하지 않고 확률에 의존하므로, 이를 명확히 설명해야 합니다.

어떤 방식을 선택할까

리전 사이의 통신이 끊겼을 때 어떤 동작이 필요한지에 따라 선택이 달라집니다.

  • 생성 결과의 전역 일관성이 쓰기 가용성보다 중요하다면, 쓰기를 결정하는 곳을 하나로 유지하거나 리전 간 합의를 요구합니다.
  • 각 리전에서 계속 생성할 수 있는 것이 더 중요하다면, 비동기 복제를 받아들이고 충돌 시 동작을 정합니다.
  • 기존 매핑은 거의 바뀌지 않으므로 리디렉션은 대체로 가용성을 우선할 수 있습니다. 다만 악용되는 단축 URL을 비활성화할 때는 변경 사항을 전 세계에 더 빠르게 전파해야 할 수 있습니다.

여러 리전을 사용하는 아키텍처에서는 일관성과 운영 방식을 결정해야 합니다. 로드 밸런서를 한 계층 더 두는 것만으로는 해결되지 않습니다.
