URL 단축 서비스 V6: 여러 리전에서 사용자 요청 처리하기

다른 대륙에 있는 사용자는 데이터베이스 조회가 거의 즉시 끝나도 네트워크 통신 때문에 기다릴 수 있습니다. 샤딩으로 매핑을 나누어 저장하고 운영할 수 있게 되었지만, 모든 샤드가 여전히 사용자와 멀리 떨어져 있습니다.

이번에는 사용자 가까이에서 읽기 요청을 처리하되, 매핑을 생성할 곳은 명확히 정해둡니다. 이어서 모든 리전이 독립적으로 쓰기 요청을 받아야 한다면 무엇이 달라지는지 살펴보겠습니다.

  • 시리즈: URL 단축 서비스 아키텍처 시리즈
  • 이전 글: V5
  • 다음 글: V7

리전 장애 때 어디까지 중단을 허용할까요?

새 요구사항은 멀리 있는 사용자의 리디렉션 지연을 줄이고, 주 리전을 사용할 수 없을 때 복구하는 것입니다. 앞선 버전처럼 생성 성공을 알린 매핑은 잃지 않아야 합니다. 이번에 대비할 장애는 서버 한 대가 아니라 리전 하나의 중단입니다.

이 서비스에서는 생성 요청이 리디렉션 요청보다 훨씬 적습니다. 이번 버전에서는 생성이 느려지고 리전 간 네트워크 단절 중에 일시적으로 중단되는 것을 허용합니다. 따라서 여러 리전에서 동시에 쓰는 것을 기본 요구사항으로 삼지 않고, 샤드마다 한 곳에서만 쓰기를 허용합니다.

캐시나 로컬 복제본에 정상적인 사본이 있는 단축 URL은 계속 조회할 수 있어야 합니다. 복구 중 매핑의 존재 여부를 확인할 수 없다면 503을 반환할 수 있습니다. 여전히 불확실한 상태를 404로 처리하지 않습니다.

자주 하는 작업을 사용자 가까이로 옮기기

샤드의 주 노드는 리전 A에 둡니다. 리전 B와 C에는 애플리케이션 인스턴스, 캐시, 읽기 복제본을 둡니다. 글로벌 라우팅은 방문자의 요청을 가까운 정상 리전으로 보냅니다. 

                         +-> region A: applications + shard primaries
global traffic routing -+-> region B: applications + cache + read copies
                         +-> region C: applications + cache + read copies

Creation in B or C -> write authority in A
Replication       -> copies in B and C

각 리전의 서비스는 V5의 버킷 매핑을 그대로 사용해 해당 샤드의 복제본을 찾습니다. 리전 간 복제를 도입하면 라우팅에서 두 가지를 판단해야 합니다. 어느 샤드가 단축 코드를 담당하는지, 어느 리전의 복제본이 이 요청에 응답할 수 있는지입니다.

비교를 위해 먼 리전과의 왕복에 160밀리초, 같은 리전 안의 왕복에 15밀리초가 걸린다고 가정합니다. 먼 리전까지 왕복하지 않으면 요청의 이 구간에서 약 145밀리초를 줄일 수 있습니다. 설명을 위한 가정값이며, 측정 결과나 특정 지역 간 지연 시간을 보장하는 수치는 아닙니다.

효과는 로컬에서 처리를 끝낼 수 있는 요청의 비율에 달려 있습니다. 방금 생성한 매핑을 조회할 때는 여전히 느린 경로를 거칠 수 있으므로, 평균뿐 아니라 꼬리 지연 시간도 살펴봐야 합니다.

A에서 만든 단축 URL을 B에서 열면

비동기 읽기 복제본에는 매핑이 늦게 반영될 수 있습니다. 

1. A commits code X.
2. Client receives X and sends it to a user in B.
3. B's cache misses.
4. B's read copy has not applied X yet.
5. B consults the current write authority.
6. B returns the redirect and may cache X.

V4에서 복제본에 매핑이 없을 때 적용했던 규칙을 이제 훨씬 느린 네트워크 너머에서도 적용합니다. 애플리케이션은 원격 조회에 충분한 시간을 배정해야 하며, 요청 처리 기한을 넘기면 일시적인 실패를 반환해야 합니다.

로컬에서 변경 불가능한 매핑을 찾았다면 바로 리디렉션을 반환할 수 있습니다. 찾지 못했다면 현재 쓰기를 담당하는 곳에 확인해야 합니다. 그곳과 통신할 수 없으면 B는 “존재하지 않는 코드”와 “존재하지만 아직 이곳에 도착하지 않은 코드”를 구분할 수 없습니다. 이때는 503을 반환합니다.

이 실패를 매핑이 없다는 뜻으로 캐시해서는 안 됩니다. 그러면 네트워크가 복구된 뒤에도 매핑이 없다고 기록한 캐시 항목 때문에 새 단축 URL을 찾지 못할 수 있습니다.

A를 잃었을 때 보존할 데이터는 복제 정책이 결정합니다

비동기 복제만 사용하면 생성 성공을 응답한 최신 매핑이 A에만 남을 수 있습니다. 다른 리전에 복제되기 전에 A를 잃으면 트래픽 경로를 바꿔도 그 매핑을 복구할 수 없습니다.

생성 성공을 응답한 매핑을 보호하려면, 각 샤드는 지정된 복구 리전에 장애 후에도 보존되는 사본을 확보한 뒤 성공을 응답해야 합니다. 이 설계에서는 복구 리전을 B라고 가정합니다. V4의 리전 내부 이중화는 유지할 수 있지만, 리전 간 사본을 대신하지는 못합니다.

생성 요청은 먼 리전의 확인 응답까지 기다려야 하므로 더 느려집니다. 필요한 리전 간 통신 경로가 끊기면 생성도 중단됩니다. 처음에 허용한 비용입니다. C는 비동기 읽기 리전으로 남을 수 있으므로, 복구 시 쓰기를 맡을 자격이 자동으로 생기지는 않습니다.

장애 후에도 보존되는 복구 기록과 쿼리로 조회할 수 있는 행은 여전히 구분해야 합니다. 승격할 후보가 매핑의 존재 여부를 최종적으로 판단하는 읽기 요청을 처리하려면, 먼저 복구 정책에서 요구하는 기록을 적용해야 합니다. PostgreSQL 복제 문서에서 확인 응답 단계의 구체적인 예를 볼 수 있습니다. 리전 장애 전환 절차 전체는 별도로 설계해야 합니다.

주 리전을 잃었을 때의 복구 순서

서비스를 복구하려면 DNS 레코드를 바꾸는 것 이상의 작업이 필요합니다.

  1. 선택한 글로벌 라우팅 방식으로 새 사용자 트래픽이 A로 가지 않게 합니다.
  2. 데이터베이스 제어 시스템의 펜싱과 소유권 규칙에 따라 A가 더 이상 쓰기를 계속할 수 없는지 확인합니다.
  3. B에서 복구 조건을 갖춘 샤드 복제본을 복구하고 승격합니다.
  4. 샤드별로 새로 쓰기를 담당할 곳을 알리고 애플리케이션 연결을 갱신합니다.
  5. 같은 정책으로 생성을 재개하기 전에, 장애 후에도 데이터를 보존할 수 있는 원격 사본을 다시 확보합니다.

이 과정의 일부 단계에서는 정상 리전의 캐시로 리디렉션을 계속 제공할 수 있습니다. 안전하게 쓰기를 맡을 곳이 없는 동안에는 아직 처리하지 못한 요청이 일시적으로 실패할 수 있습니다.

라우팅을 바꿔도 기존 연결이 즉시 옮겨지거나 캐시된 모든 DNS 응답이 무효화되지는 않습니다. 복구 테스트에는 여전히 이전 경로로 접속하는 클라이언트와 오래된 샤드 맵을 가진 애플리케이션을 포함해야 합니다.

A가 파괴되지 않고 네트워크에서 격리되기만 했다면, 양쪽에서 독립적으로 쓰기 노드를 승격할 경우 서로 쓰기 권한을 주장하게 됩니다. 쓰기를 거부해야 하더라도 한 곳에서만 쓰는 정책을 유지합니다. 복구 시 어느 쪽에 쓰기를 맡길지 결정하는 조정 시스템도 대비하려는 리전 장애가 발생했을 때 계속 동작해야 합니다. 제어기가 A에만 있다면 설계에 빈틈이 남습니다.

승격 후에도 다른 원격 사본에 데이터가 모두 반영될 때까지 생성이 중단될 수 있습니다. 생성 성공을 응답한 데이터를 하나도 잃지 않으면서 어떤 네트워크 단절에서도 쓰기를 계속하려면, 지금과는 다른 보장 조건이 필요합니다.

모든 리전에서 단축 URL을 만들어야 한다면

이제 제품이 생성 중단을 허용할 수 없다고 가정합니다. 격리된 리전의 호출자도 다른 리전에 접속하지 않고 사용할 수 있는 새 단축 URL을 받아야 합니다.

무작위 코드를 쓰면 각 리전이 독립적으로 후보를 만들 수 있지만, 로컬 유일성 제약은 로컬 데이터만 확인합니다. 두 리전이 같은 코드를 서로 다른 원본 URL에 배정하고 모두 성공을 응답할 수 있습니다. 나중에 충돌을 발견해도 하나의 공개 경로로 두 약속을 모두 지킬 수는 없습니다.

다음과 같은 선택지가 있습니다.

전략 생성 시 동작
전역에서 공유하는 코드 예약 예약을 담당하는 곳의 응답을 기다리므로, 격리된 리전에서는 생성하지 못할 수 있습니다
리전별로 겹치지 않는 코드 공간 리전에 영구 배정된 공간 안에서 코드를 만들고 로컬 충돌을 확인합니다
큰 무작위 코드 공간만 사용 전역 유일성을 엄격히 보장하는 대신, 정량화한 충돌 위험을 받아들입니다

코드 공간을 나눈다면, 그 외에는 내부 의미를 드러내지 않는 코드에 리전 식별자를 포함할 수 있습니다. 리전별로 배정한 공간은 절대 겹치면 안 되며, 함부로 재사용해서도 안 됩니다. 각 리전에는 여전히 로컬 유일성 보장과 복제가 필요합니다. 접두사가 있다고 데이터가 장애 후에도 보존되는 것은 아닙니다.

이 방식으로도 연결이 끊긴 다른 리전에서 새 매핑을 즉시 읽을 수는 없습니다. 모든 리전에서 즉시 조회할 수 있다는 요구를 완화하거나, 코드를 만든 리전으로 읽기 요청을 보내야 합니다. 더 강한 보장을 응답하려면 복제가 끝날 때까지 기다려야 합니다. 유일성을 해결해도 언제 조회할 수 있는지, 리전 장애 때 데이터를 보존할 수 있는지는 별도로 정해야 합니다.

이 시리즈에서는 앞서 정한 우선순위에 맞춰 한 곳에서만 쓰기를 담당하는 설계를 유지합니다. 제품이 그 우선순위를 명시적으로 바꿀 준비가 되었다면 다른 선택지가 유용합니다. Dynamo 논문은 장애 중에도 갱신을 받아들이고 나중에 버전을 조정할 때 어떤 결과가 생기는지 이해하는 데 도움이 됩니다.

변경 불가능한 매핑도 모든 리전에서 차단해야 할 수 있습니다

원본 URL이 바뀌지 않는 동안에는 기존 매핑으로 리디렉션하기 쉽습니다. 하지만 악용되는 단축 URL을 비활성화하려면 바뀔 수 있는 상태를 추가해야 합니다.

A에서 내린 비활성화 결정은 B와 C의 캐시에 늦게 도착할 수 있습니다. 캐시 수명을 짧게 하면 일부 오래된 응답이 계속되는 시간을 제한할 수 있지만, 모든 리전에서 즉시 차단되지는 않습니다. 더 엄격한 보장을 하려면 최신 차단 목록을 확인하거나, 필요한 정책 상태를 확인할 수 없는 곳에서는 리디렉션을 거부해야 할 수 있습니다.

여기서도 무엇을 우선할지 분명히 해야 합니다. 격리 중에도 캐시된 단축 URL로 리디렉션하면 가용성을 우선합니다. 정책이 최신임을 확인할 때까지 리디렉션을 거부하면 정책 적용을 우선합니다. 제품에서 차단까지 허용할 지연을 정해야 하며, 모든 캐시 계층이 이를 따라야 합니다.

무엇을 측정할까요?

리전별로 로컬에서 요청을 완료한 비율, 원격 조회로 넘어간 요청, 복제 지연, 생성 지연, 복구 시간을 측정합니다. 새 단축 URL을 다른 리전에서 여는 경우, 쓰기를 담당하는 리전이 격리된 경우, 라우팅 정보가 오래된 경우, 네트워크 단절 중에 비활성화를 결정한 경우를 테스트합니다. 제안하는 점검 항목이며, 측정 결과는 아닙니다.

이제 설계에는 리전별 읽기 경로와 복구 중 쓰기를 맡을 곳이 정해져 있습니다. V7에서는 지연에 민감한 이 경로가 분석 데이터베이스를 기다리지 않도록 하면서 클릭 집계를 추가합니다.
