URL 단축 서비스: 문제 정의와 설계 로드맵

이 시리즈에서는 긴 URL을 공유하기 좋은 단축 URL로 바꾸는 URL 단축 서비스를 설계하려고 합니다. 누군가 짧은 URL을 열면 원본 주소로 보내주는 서비스입니다.

이 포스트에서는 우리의 URL 단축 서비스가 해야 할 일과 요청이 실패했을 때의 동작, 설계에 사용할 가정을 정리합니다. 또한, 이후 버전에서 풀어갈 문제들과 요구사항도 살펴봅니다. 우선 첫 번째 설계는 V1에서 애플리케이션 서버 한 대와 데이터베이스 하나로 시작합니다.

단축 URL을 열면 일어나는 일

우리의 서비스는 단축된 URL 코드와 원본 URL 사이의 매핑을 저장합니다. 클라이언트가 URL 단축을 요청하면 다음과 같은 단축 URL을 반환합니다. 

https://sho.rt/aB3xQ9

이 URL을 열면 서비스는 aB3xQ9 에 연결된 원본 URL을 찾아 클라이언트를 그 주소로 리디렉션합니다. 클라이언트는 단축 코드로 원본 URL에 도달할 수 있으면 됩니다. 클라이언트는 URL-agnostic, 즉 단축 URL이 어떻게 만들어졌는지에 따라 동작이 달라져서는 안 됩니다. 코드를 순서대로 만들지, 무작위로 만들지, 다른 방식으로 할당할지는 V1에서 결정합니다.

기능 요구사항

단축 URL 만들기

입력
Absolute URL로 표현한 원본 URL입니다.
성공
단축 코드 할당과 원본 URL 매핑 저장을 하나의 원자적 트랜잭션으로 처리합니다. 커밋된 매핑은 저장소가 보장하는 범위의 장애가 발생해도 보존되어야 합니다. 트랜잭션이 커밋된 뒤에만 단축 URL을 반환합니다.
거부
원본 URL이 서비스의 URL 정책에 맞지 않으면 검증 오류를 반환하고 매핑을 만들지 않습니다.
저장 실패
매핑을 커밋할 수 없으면 생성에 성공했다고 응답하지 않습니다.

HTTP 인터페이스는 다음과 같이 구성할 수 있습니다. 

POST /links
Content-Type: application/json

{"url":"https://example.com/articles/a-long-path"}

생성에 성공하면 201 Created 로 응답하고 새로 만든 리소스를 알려줍니다. 

HTTP/1.1 201 Created
Location: https://sho.rt/aB3xQ9
Content-Type: application/json

{"short_url":"https://sho.rt/aB3xQ9"}

원본 URL이 서비스 정책에 맞지 않으면 생성 트랜잭션을 시작하기 전에 요청을 거부합니다. 

HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"invalid_destination_url"}

이 경우에는 코드도 매핑도 만들지 않습니다.

서비스가 커밋된 데이터를 장애 후에도 보존하는 저장소를 사용할 수 없다고 판단했고 매핑도 커밋할 수 없다면, 단축 URL을 반환하는 대신 일시적으로 요청을 처리할 수 없다고 응답합니다. 

HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json

{"error":"link_storage_unavailable"}

단축 URL로 이동하기

입력
요청 경로에 담긴 단축 코드입니다.
성공
매핑이 있는 코드라면 저장된 원본 URL을 Location 헤더에 담아 리디렉션 응답을 반환합니다.
알 수 없는 코드
매핑이 없으면 404 Not Found 를 반환합니다.
저장소 장애
매핑이 있는지 확인할 수 없으면 일시적으로 요청을 처리할 수 없다고 응답합니다. 알 수 없는 코드라고 응답해서는 안 됩니다.

클라이언트는 다음과 같은 요청으로 단축 URL에 접속합니다. 

GET /aB3xQ9
Host: sho.rt

매핑이 있는 코드라면 응답에 저장된 원본 URL을 담습니다. 

HTTP/1.1 302 Found
Location: https://example.com/articles/a-long-path

매핑이 없는 코드라면 다음과 같이 응답합니다. 

HTTP/1.1 404 Not Found
Content-Type: application/json

{"error":"short_link_not_found"}

저장소를 사용할 수 없어 조회를 마치지 못했다면, 매핑이 없는 경우와 구분해서 응답합니다. 

HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json

{"error":"link_lookup_unavailable"}

이 경우에 404 를 반환하면 클라이언트는 일시적인 인프라 장애와 매핑이 실제로 없는 경우를 구분할 수 없게 됩니다.

302 Found 를 사용하면 이후에 같은 단축 URL을 방문할 때도 URL 단축 서비스를 거치게 됩니다. 원본 URL이 바뀌지 않는 링크에 영구 리디렉션을 사용할지는 제품 정책으로 따로 결정합니다. 클라이언트가 영구 리디렉션을 캐시할 수 있기 때문입니다.

기본 가정

  • 같은 원본 URL을 가리키는 링크가 이미 있어도 생성 요청마다 새 단축 URL을 만듭니다.
  • 원본 URL은 HTTP 또는 HTTPS 절대 URL이어야 합니다.
  • 기본 설계에서는 링크가 만료되거나 바뀌지 않습니다.
  • 원본 URL로 리디렉션할 뿐, 그 URL의 콘텐츠를 가져오지는 않습니다.

버전마다 달라지는 요구사항

각 글에서는 앞서 정한 기본 동작을 유지하면서 다음 다섯 가지 요구사항을 바꿔갑니다.

  • 요청량과 리디렉션 요청 대 생성 요청의 비율입니다.
  • 누적된 매핑 수와 필요한 저장 공간입니다.
  • 서버, 데이터베이스, 리전 장애를 어느 범위까지 견뎌야 하는지입니다.
  • 링크를 만들거나 비활성화한 직후에 필요한 일관성입니다.
  • 분석처럼 비동기로 처리해도 되는 작업입니다.

어느 한 요구사항이 커졌다고 해서 이후 버전에 나오는 구성 요소가 모두 필요한 것은 아닙니다. 예를 들어 애플리케이션 서버를 여러 대 둔다는 이유만으로 캐시가 필요해지지는 않습니다. 데이터를 파티션으로 나눈다고 데이터가 복제되는 것도 아닙니다.

설계 로드맵

설계는 한 버전씩 확장합니다. 각 글에서 요구사항을 하나 추가하고, 이전 설계가 그 요구사항을 충족하지 못하는 지점을 살펴봅니다. 그런 다음 문제를 해결하는 데 필요한 최소한의 변경을 도입합니다. 이 과정에서 사용하는 숫자는 설명을 위한 가정이며, 실제 서비스에서 측정한 값이 아닙니다.

각 단계에서 무엇을 바꾸고 왜 바꾸는지는 아래 표에 정리했습니다.

글 새 요구사항 이전 설계의 한계 설계 변경
V1 많지 않은 요청을 처리하면서 매핑을 영속적으로 저장해야 합니다 재시작하면 메모리에 저장한 데이터가 사라집니다 애플리케이션 서버 한 대와 데이터베이스 하나를 둡니다
V2 애플리케이션 서버 한 대에 장애가 발생해도 동작해야 합니다 요청을 처리하는 경로가 프로세스 하나뿐입니다 로드 밸런서와 상태를 저장하지 않는 인스턴스를 둡니다
V3 훨씬 많은 리디렉션 요청을 처리해야 합니다 모든 리디렉션 요청이 데이터베이스까지 갑니다 매핑을 저장하는 분산 캐시를 둡니다
V4 데이터베이스 서버 한 대에 장애가 발생해도 동작해야 합니다 캐시는 커밋된 데이터를 장애 후에도 보존하는 저장소가 아닙니다 복제와 장애 조치를 도입합니다
V5 데이터베이스 하나의 운영 한계를 넘는 규모의 데이터를 처리해야 합니다 복제본은 데이터를 복사할 뿐 나눠 저장하지 않습니다 매핑 저장소를 파티션으로 나눕니다
V6 멀리 있는 사용자의 지연 시간과 리전 장애 위험을 줄여야 합니다 한 곳에만 배포하면 먼 사용자는 지연이 크고, 전체가 한 리전의 장애 영향을 받습니다 리전별 읽기와 전역 라우팅을 도입합니다
V7 리디렉션을 늦추지 않고 클릭을 기록해야 합니다 카운터를 동기로 갱신하면 읽기 요청을 처리할 때 쓰기도 해야 합니다 비동기 이벤트 파이프라인을 둡니다

시리즈 전체에서 같은 방식으로 문제를 풀어갑니다.

  1. 새 요구사항을 분명히 밝히고, 도움이 된다면 수치로 나타냅니다.
  2. 해당 작업이 이전 설계에서 어떤 경로를 거치는지 따라갑니다.
  3. 어떤 자원이나 보장이 요구사항에 못 미치는지, 어느 범위의 장애를 견디지 못하는지 정확히 짚습니다.
  4. 문제를 해결하는 데 필요한 최소한의 장치를 추가합니다.
  5. 변경한 지점의 처리 용량이나 지연 시간을 다시 계산합니다.
  6. 새로 생기는 장애 유형과 운영 비용을 설명합니다.
  7. 관련 없는 문제는 이후 버전에서 다룹니다.

이렇게 비교하면 어떤 문제 때문에 설계를 바꾸었는지 따라갈 수 있습니다. 구성 요소를 추가해서 무엇을 얻는지, 그와 함께 어떤 복잡성이 생기는지도 볼 수 있습니다.

설계 변화 한눈에 보기

V1부터 V7까지 설계가 정리되면 각 글의 다이어그램을 하나씩 이 페이지에 가져올 예정입니다. 다이어그램은 같은 시각적 표현을 사용하고, 해당 버전에서 추가한 구성 요소나 데이터 흐름을 강조합니다. 한곳에 모아두면 설계가 어떻게 달라졌는지 눈으로 따라갈 수 있습니다. 각 글에서 설계 이유를 설명하는 부분은 다이어그램으로 대신하지 않습니다.
