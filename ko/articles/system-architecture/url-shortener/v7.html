URL 단축 서비스 V7: 리디렉션을 늦추지 않고 클릭 기록하기

링크를 공유한 사람은 누군가 그 링크를 열었는지 알고 싶어 합니다. 리디렉션할 때마다 카운터를 올릴 수도 있지만, 그러면 이 시리즈에서 줄곧 빠르게 처리하도록 다듬어 온 리디렉션 경로에 쓰기 작업이 추가됩니다.

이번에는 클릭 이벤트를 별도 경로로 보내고, 그 경로가 느려졌을 때 어떻게 처리할지 정하겠습니다. 비동기 처리가 도움이 되려면 큐, 재시도, 데이터 유실에 관한 규칙부터 정해야 합니다.

  • 시리즈: URL 단축 서비스 아키텍처 시리즈
  • 이전 글: V6
  • 다음 글: 현재 시리즈는 여기서 마칩니다

무엇을 클릭으로 셀지 정하기

제품에는 링크별, 시간별, 지역별 클릭 횟수가 필요합니다. 집계 결과는 늦게 나와도 되고, 이벤트가 가끔 누락되어도 괜찮습니다. 다만 분석 때문에 리디렉션 지연이 눈에 띄게 늘어나서는 안 됩니다.

여기서 클릭 이벤트는 서비스가 유효한 리디렉션 요청을 처리했다는 뜻입니다. 사람이 클릭했는지, 브라우저가 응답을 받았는지, 원본 페이지가 로드되었는지까지는 알 수 없습니다. 봇, 미리보기, 클라이언트 재시도도 요청을 만들 수 있습니다. 순 방문자 수나 부정 트래픽을 보정한 클릭 횟수를 구하려면 별도의 정의가 필요합니다.

V1의 no-store 리디렉션 정책을 유지합니다. 이 정책을 따르는 캐시라면 반복 요청에도 저장된 응답을 재사용하지 않고 서비스에 접속합니다. 그래도 요청 횟수는 URL 단축 서비스에 들어온 트래픽을 관찰한 값이며, 페이지가 성공적으로 열린 횟수를 측정한 값은 아닙니다.

매핑 행에 카운터를 두면 생기는 문제

인기 있는 단축 코드에 1초 동안 요청 1만 건이 들어온다고 가정합니다. 각 요청을 처리할 때 응답을 보내기 전에 같은 데이터베이스 행의 카운터를 올리면, 같은 값을 갱신하려는 작업들이 서로 경쟁합니다.

매핑을 샤딩해도 이 카운터 하나가 여러 샤드로 분산되지는 않습니다. 분석용 쓰기 때문에 리디렉션이 늦어질 수 있고, 카운터 저장소를 사용할 수 없으면 유효한 링크도 작동하지 않을 수 있습니다.

그래서 집계 경로를 따로 둡니다. 

                           +-> cache / mapping store -> redirect response
redirect application -----+
                           +-> bounded local buffer
                                  -> event log -> consumers -> analytics store

버퍼에서 생길 수 있는 장애도 설계에 포함해야 합니다. 문제가 해결될 때까지 쓰기 작업을 무한정 쌓아 둘 수는 없습니다.

이벤트 전달 규칙 정하기

이번 버전에서는 요청 핸들러가 유효한 매핑을 찾은 뒤 대기 없이 이벤트를 큐에 넣으려고 시도합니다. 백그라운드 전송 프로세스는 버퍼의 이벤트를 배치로 묶어 복제된 로그에 보냅니다. 요청 핸들러는 로그가 배치 저장을 확인해 줄 때까지 기다리지 않고 리디렉션 응답을 보냅니다.

이벤트에는 다음 필드를 담을 수 있습니다. 

event_id:       one stable ID for this event
code:           the resolved short code
occurred_at:    time the service handled the request
request_region: the region serving the request

전송 프로세스는 이벤트가 로그에 추가되었는지 확실하지 않아 재시도할 때도 같은 이벤트 ID를 사용합니다. 전달을 시도할 때마다 새 ID를 만들지 않습니다.

정해 둔 집계에 필요한 필드만 수집합니다. IP 주소나 전체 user-agent 문자열을 추가하면 개인정보와 보관 정책도 고려해야 합니다. 앞서 정한 클릭 횟수를 세는 데는 이런 정보가 필요하지 않습니다.

로그에 도달하기 전에 이벤트가 유실될 수 있는 경우는 두 가지입니다. 로컬 버퍼가 가득 차거나, 아직 보내지 않은 이벤트를 버퍼에 둔 채 애플리케이션이 비정상 종료될 수 있습니다. 어느 경우든 리디렉션은 계속 제공하지만, 집계된 횟수는 실제보다 적을 수 있습니다. 근삿값을 정확한 값으로 오인하지 않도록 버퍼에서 버린 이벤트 수와 전송 실패를 운영 지표로 기록합니다.

요청을 처리하는 단계에서는 이벤트 전달을 시도하되 성공까지 보장하지 않는 best-effort 정책을 의도적으로 선택합니다. 나중에 제품에서 수락한 모든 리디렉션 요청의 감사 기록을 요구한다면, 더 강한 확인 절차에 비용을 들이거나 요청 수락 규칙을 바꿔야 합니다.

로그 용량과 복구에 필요한 처리량 계산하기

V3의 평균 요청률과 이벤트당 원시 데이터 200바이트를 기준으로 계산합니다. 

3,860 events/second * 200 bytes * 86,400 seconds
  = 66,700,800,000 bytes/day
  = about 66.7 GB/day

최대 요청률에서는 다음과 같습니다. 

40,000 events/second * 200 bytes = 8 MB/second

여기에 복제, 레코드 메타데이터, 인덱스, 프로토콜 오버헤드를 더해야 합니다. 3일 치 원시 이벤트는 약 200 GB이며, 같은 데이터를 총 세 벌 보관하면 오버헤드를 제외해도 약 600 GB입니다.

보관 기간은 소비자가 얼마나 오래 뒤처져도 되는지를 알려 주지만, 밀린 이벤트를 얼마나 빨리 처리할 수 있는지는 알려 주지 않습니다. 예를 들어 평균 요청률에서 소비자가 한 시간 동안 멈추면 다음만큼 쌓입니다. 

3,860 * 3,600 = 13,896,000 events of backlog

If consumers process 8,000 events/second after recovery:
net drain rate = 8,000 - 3,860 = 4,140 events/second
catch-up time  = 13,896,000 / 4,140 = about 56 minutes

이 계산에서는 새 이벤트가 계속 평균 요청률로 들어오고, 소비자가 제시한 처리량을 유지한다고 가정합니다. 둘 다 설명을 위한 가정입니다. 소비자가 새로 들어오는 만큼만 처리한다면 밀린 이벤트는 줄어들지 않습니다.

최대 요청률에서 10초 치 이벤트를 담는 로컬 버퍼에는 이벤트 40만 건이 들어갑니다. 전체 서버에 걸쳐 원시 데이터만 약 80 MB이며, 객체 오버헤드도 추가됩니다. 로그 장애가 길어지면 이 용량을 넘으므로, 버퍼 크기에 상한을 두고 버린 이벤트 수를 기록하면서 리디렉션을 계속 제공합니다.

반복 전달된 이벤트를 한 번만 집계하기

전송 프로세스가 이벤트를 로그에 성공적으로 추가하고도 확인 응답을 받지 못할 수 있습니다. 재시도하면 같은 이벤트가 로그에 다시 들어갈 수 있습니다. 소비자도 이벤트를 처리한 뒤 진행 상황을 기록하기 전에 비정상 종료될 수 있습니다.

이벤트 E를 집계한 뒤 소비자가 비정상 종료되었다고 가정합니다. 

1. Read E.
2. Increment the hourly counter.
3. Crash before acknowledging progress.
4. Restart and receive E again.

2단계를 그대로 반복하면 E를 두 번 세게 됩니다. 이런 중복 전달을 걸러 내려면 분석 저장소에 처리한 이벤트 ID를 보관하고 유일성 제약을 둘 수 있습니다.

소비자는 하나의 로컬 트랜잭션에서 다음을 수행합니다. 

begin transaction
insert event ID into the processed-events table
if the ID was newly inserted:
    increment the aggregate for code, time bucket, and region
commit transaction
acknowledge consumer progress afterward

트랜잭션이 실패하면 ID 삽입과 집계 갱신 모두 커밋되지 않습니다. 커밋 후 진행 상황을 알리는 확인 응답이 유실되어도, 재처리할 때 기존 ID를 발견하므로 횟수를 올리지 않습니다. ID 삽입과 카운터 갱신을 별도 트랜잭션으로 처리하면 두 작업 사이에 비정상 종료가 일어날 여지가 다시 생깁니다.

중복 제거용 저장소에도 용량과 보관 정책이 필요합니다. 재처리 시 중복 제거를 보장하는 기간만큼은 ID를 남겨 두어야 합니다. ID를 지운 뒤 오래된 이벤트를 재처리하면 다시 집계될 수 있습니다.

이 정책이 정한 범위에서는 처리한 이벤트를 한 번만 집계한다고 명확히 보장할 수 있습니다. 하지만 로그에 도달하기 전에 버린 이벤트는 복구하지 못합니다. 클라이언트 재시도로 생긴 서로 다른 리디렉션 요청도 하나로 합치지 않습니다. 여기서 정한 집계 기준으로는 각각 별개의 이벤트입니다.

Kafka의 이벤트 전달 보장 문서에서도 같은 경계를 중요하게 다룹니다. 외부 저장소에 결과를 쓸 때는 결과 저장과 소비자의 진행 상황 기록을 조율해야 합니다. 로그의 전달 설정만으로 이후의 모든 작업이 정확히 한 번 수행되지는 않습니다.

집계 경로도 확장하기

이벤트 로그를 단축 코드만으로 파티셔닝하면 인기 있는 링크 하나 때문에 특정 파티션에 작업이 몰릴 수 있습니다. 이 집계에는 모든 클릭의 전역 순서가 필요하지 않으므로, 이벤트 ID 등을 기준으로 더 넓게 분산할 수 있습니다.

소비자는 배치 단위로 집계한 뒤 결과를 쓸 수 있습니다. 규모가 더 커지면 카운터를 나누어 관리하고 보고할 때 합칠 수도 있습니다. 그러면 전역 행 하나에 갱신이 몰려 리디렉션 경로에서 없앤 카운터 문제가 되풀이되는 일을 피할 수 있습니다. 부분 집계에서도 중복 처리 규칙이 맞아야 하며, 재시도할 때 같은 배치를 두 번 더해서는 안 됩니다.

시간별 집계에는 소비자가 뒤늦게 처리한 시각 대신 이벤트 발생 시각을 사용합니다. 늦게 도착한 이벤트는 이전 시간 구간의 집계를 갱신할 수 있습니다. 시계 오차 때문에 정확도에는 여전히 한계가 있으므로, 보고서에는 집계가 얼마나 최신인지 보여 주어야 합니다. 가장 최근 구간의 집계가 완료된 것처럼 표현해서는 안 됩니다.

분석 경로에 장애가 나면

로그를 사용할 수 있는 상태에서 소비자만 멈추면 전송 프로세스는 계속 이벤트를 추가할 수 있습니다. 가장 오래된 미처리 이벤트의 경과 시간과 남은 보관 기간에 대한 알림으로, 재처리할 데이터를 잃기까지 얼마나 여유가 있는지 파악합니다.

로그를 사용할 수 없으면 전송 프로세스는 정해진 한도 안에서 재시도하고, 버퍼는 차오릅니다. 버퍼가 가득 차면 선택한 정책에 따라 분석 이벤트를 버리고 버린 이벤트 수를 지표에 반영합니다. 리디렉션 핸들러를 무기한 기다리게 하거나 메모리를 끝없이 사용하지는 않습니다.

복구할 때는 밀린 작업을 서서히 처리해야 합니다. 캐시가 비어 있을 때 매핑 데이터베이스에 부하가 몰리는 것처럼, 전송 재시도와 소비자의 밀린 작업 처리가 한꺼번에 몰리면 로그와 분석 저장소도 과부하에 빠질 수 있습니다.

처리 비용이 큰 악용 분류 작업은 이 이벤트를 별도로 소비할 수 있습니다. 비활성화 결정이 확정되면 매핑과 정책 시스템으로 전달합니다. 실제로 리디렉션이 중단되는 시점은 V3의 캐시 규칙과 V6의 리전 간 전파 규칙에 따라 정해집니다. 분석이 얼마나 늦어지는지와 즉시 차단을 보장하는지는 구분해야 합니다.

설계를 마무리하려면

집계 결과를 신뢰하기 전에 중복 전달을 주입하고, 트랜잭션 커밋 전후에 소비자를 비정상 종료시키고, 생산자 버퍼를 가득 채우고, 로그를 중단해 봐야 합니다. 집계된 횟수와 리디렉션 지연을 함께 확인합니다. 이는 구현 시 수행하도록 제안하는 검증 항목이며, 이 글의 용량 수치는 실측값이 아닙니다.

이 시리즈는 데이터베이스 하나에 저장한 매핑에서 시작했습니다. 각 버전에서는 명시한 문제를 해결하기 위해 애플리케이션 처리 경로를 추가하고, 읽기 결과를 캐시하고, 장애 후에도 데이터를 보존하는 데이터베이스 사본을 두었습니다. 이어서 저장소를 분할하고, 리전별로 접근할 수 있게 하고, 마지막으로 비동기 집계를 도입했습니다. 그때마다 서비스가 기다리거나, 작업을 거절하거나, 선택적으로 수집하는 데이터를 잃는 조건도 추가되었습니다. 이런 조건도 사용자가 경험하는 아키텍처의 일부입니다.
