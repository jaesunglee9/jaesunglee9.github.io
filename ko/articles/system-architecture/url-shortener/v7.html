URL 단축 서비스 V7: 리디렉션을 늦추지 않고 클릭 기록하기

시리즈 안내

이 글은 URL 단축 서비스 아키텍처 시리즈의 V7입니다.

  • 이전: V6
  • 다음: 현재 시리즈는 여기까지입니다

새로 필요한 기능

사용자는 링크별, 시간별, 지역별 클릭 수를 원합니다. 집계 결과가 늦게 나오거나 때때로 근삿값이어도 괜찮지만, 분석 때문에 리디렉션이 눈에 띄게 느려져서는 안 됩니다.

기존 설계의 한계

리디렉션마다 매핑 행의 카운터를 갱신하면 읽기 위주였던 처리 경로가 쓰기 위주로 바뀝니다. 인기 있는 링크에는 여러 클라이언트의 요청이 몰려 같은 카운터를 갱신하려고 경합합니다. 분석 시스템에 장애가 나면 리디렉션까지 중단될 수 있습니다.

최소한의 설계 변경

클릭 이벤트를 로그에 추가하고, 리디렉션에 필요한 매핑 조회와 별개로 집계합니다. 

                         +-> cache / mapping store -> redirect
redirect application ---+
                         +-> event log -> consumers -> analytics store

이벤트에는 단축 코드, 타임스탬프, 요청이 온 지역, 그리고 의도적으로 고른 소량의 메타데이터를 담을 수 있습니다. 컨슈머는 단축 코드에 해당하는 원본 URL을 찾는 작업과 별개로 이벤트를 집계해 보고용 테이블에 저장합니다.

V3의 평균인 초당 약 3,860건의 리디렉션에서 건당 원시 이벤트 데이터가 200바이트라면, 하루 데이터 양은 다음과 같습니다. 

3,860 events/second * 200 bytes * 86,400 seconds
  = about 67 GB/day of raw events

요청이 초당 40,000건까지 몰릴 때는 이벤트 로그가 일시적으로 초당 약 8 MB를 받아들여야 합니다. 로그 자체의 복제와 프로토콜 오버헤드는 여기에 추가됩니다.

이벤트 전달과 집계 방식

애플리케이션은 로그가 이벤트를 장애 후에도 보존하도록 기록했다는 확인 응답을 기다릴 수 있습니다. 그러면 유실은 줄지만, 요청 처리도 로그의 응답에 의존하게 됩니다. 기다리지 않고 이벤트를 보내면 리디렉션이 로그에 덜 의존하는 대신 장애가 발생했을 때 이벤트가 유실될 수 있습니다. 최소 한 번 전달하는 방식에서는 이벤트가 중복될 수 있으므로, 컨슈머가 이벤트 ID를 사용하거나 집계 결과가 근삿값일 수 있음을 받아들여야 합니다.

어느 쪽을 택할지는 제품에서 결정할 사항입니다. “정확히 한 번” 처리는 큐 설정만 바꾸면 별다른 비용 없이 얻을 수 있는 보장이 아닙니다. 프로듀서, 로그, 컨슈머, 분석 저장소가 처리한 이벤트를 어떻게 식별하고 커밋할지 합의해야 합니다.

파이프라인이 멈추더라도 리디렉션은 계속되어야 하며, 로그는 나중에 처리할 이벤트를 보관해야 합니다. 보관 용량에 따라 컨슈머의 처리가 얼마나 오래 밀려도 분석 데이터를 잃지 않을지가 결정됩니다.

악용 대응에서도 신중하게 경로 분리하기

요청 속도 제한과 대략적인 악용 검사는 엣지에서 동기적으로 처리할 수 있습니다. 비용이 많이 드는 분류와 보고 작업은 이벤트 스트림을 비동기적으로 읽어 처리할 수 있습니다. 악성으로 확인된 링크를 비활성화할 때는 다시 매핑 시스템에서 처리해야 합니다. 이때 캐시 무효화와 리전 간 전파에 걸리는 시간이 리디렉션을 얼마나 빨리 중단할 수 있는지를 결정합니다.

V7에서는 지연 시간에 민감한 조회 경로에서 보고 작업을 분리하고, 어느 정도의 지연과 유실을 허용할지 명확히 합니다.
