URL 단축 서비스 V2: 애플리케이션 서버 장애에도 서비스 유지하기

시리즈 안내

이 글은 URL 단축 서비스 아키텍처 시리즈의 V2입니다.

  • 이전: V1
  • 다음: V3

새로운 요구사항

애플리케이션 서버 한 대에 장애가 생겨도 서비스가 잠시 중단되는 일은 더 이상 허용하지 않습니다. 새 애플리케이션 버전을 배포할 때도 리디렉션이 끊기지 않아야 합니다. 트래픽과 저장 규모는 V1 수준을 유지합니다.

V1의 한계

V1에서는 요청을 받는 프로세스를 거쳐야만 데이터베이스에 접근할 수 있습니다. 데이터가 온전히 남아 있어도 프로세스의 비정상 종료, 서버 장애, 배포로 인해 서비스 전체에 접근할 수 없게 됩니다.

최소한의 설계 변경

로드 밸런서 뒤에서 애플리케이션 인스턴스를 여러 개 실행하도록 바꿉니다. 

                         +----------------+
                     +-->| application 1  |--+
client -> load balancer  +----------------+  |
                     |                       +--> database
                     +-->| application 2  |--+
                         +----------------+

각 인스턴스는 기준 데이터를 로컬에 보관하지 않습니다. 요청은 정상 동작하는 어느 인스턴스로든 전달할 수 있으며, 데이터베이스를 최종 기준으로 삼습니다. 로드 밸런서는 상태 확인에 실패한 인스턴스로 요청을 보내지 않습니다.

무작위 단축 코드 생성 방식은 이미 여러 인스턴스가 동시에 데이터를 쓰는 경우를 지원합니다. 각 인스턴스는 독립적으로 후보 코드를 생성합니다. 드물게 두 인스턴스가 같은 코드를 제안하면 데이터베이스의 기본 키 제약으로 충돌을 처리합니다.

얻는 것과 감수할 비용

남은 인스턴스에 충분한 처리 용량이 있다면 인스턴스 하나에 장애가 생겨도 애플리케이션 계층은 계속 동작할 수 있습니다. 배포할 때는 인스턴스를 점진적으로 교체할 수 있습니다. 대신 로드 밸런서 자체도 이중화해야 하며, 데이터베이스는 여전히 단일 장애점입니다.

V2에는 캐시를 추가하지 않았습니다. 애플리케이션 계층의 이중화와 데이터베이스의 읽기 처리 용량은 서로 다른 요구사항입니다.
