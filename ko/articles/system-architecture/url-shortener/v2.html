URL 단축 서비스 V2: 애플리케이션 서버 장애에도 서비스 계속하기

링크를 안전하게 저장했더라도 사용하지 못할 수 있습니다. V1에서는 애플리케이션 서버 하나를 통해서만 링크에 접근할 수 있습니다. 그 프로세스가 멈추면 데이터베이스가 정상이어도 모든 리디렉션이 멈춥니다.

이번에는 같은 데이터에 접근할 요청 경로를 하나 더 마련합니다. 서버가 멈춘 뒤 나머지 시스템이 이를 알아차릴 때까지 어떤 일이 생기는지 살펴보겠습니다.

  • 시리즈: URL 단축 서비스 아키텍처 시리즈
  • 이전 글: V1
  • 다음 글: V3

서버 장애가 나면 어디까지 보장할까요?

트래픽이 몰리는 시간대의 요청량은 여전히 초당 생성 약 4건, 리디렉션 약 40건입니다. 저장 공간이 늘어나는 속도도 그대로입니다. 새 요구사항은 애플리케이션 서버 하나에 장애가 나더라도 누군가 수리할 때까지 서비스 중단이 이어져서는 안 된다는 것입니다.

장애를 즉시 감지할 수는 없습니다. 장애가 난 서버에서 이미 처리 중이던 요청은 실패할 수 있고, 상태 확인을 통해 그 서버를 제외하기 전까지 새 요청 몇 건이 그 서버로 갈 수도 있습니다. 목표는 감지에 걸리는 시간을 일정 범위로 제한하고, 감지 후 요청 경로를 자동으로 복구하는 것입니다. 계획된 배포에서는 서버를 멈추기 전에 요청을 마무리해 이런 실패 구간을 피해야 합니다.

어떤 장애에서도 모든 요청이 성공한다고 약속하는 것보다 이처럼 보장 범위를 정하는 편이 더 유용합니다. 장애 감지 시간, 실패한 요청 수, 남은 처리 용량을 각각 측정할 수 있기 때문입니다.

같은 매핑을 사용하는 애플리케이션 인스턴스 두 개

서로 다른 서버에서 실행하는 애플리케이션 인스턴스 두 개 앞에 로드 밸런서를 둡니다. 

                         +-> application A --+
client -> load balancer -+                   +-> database
                         +-> application B --+

로드 밸런서는 요청마다 정상인 인스턴스를 선택합니다. 방문자가 단축 URL에 접근할 때 링크를 생성한 인스턴스로 요청을 보낼 필요는 없습니다.

예를 들어 A가 매핑을 생성하고 나중에 B가 그 매핑을 조회할 수 있습니다. 둘 다 같은 데이터베이스를 사용하고 단축 코드를 같은 방식으로 해석합니다. V1의 후보 코드 생성 방식과 기본 키 규칙은 이미 여러 인스턴스가 동시에 데이터를 쓰는 경우를 허용합니다.

여기서 “상태를 갖지 않는 애플리케이션 인스턴스”란 이런 뜻입니다. 인스턴스에도 메모리, 연결 풀, 임시 작업은 있습니다. 다만 이런 로컬 상태가 사라져도 성공 응답을 보낸 매핑이 유실되어서는 안 되며, 요청을 특정 인스턴스에서만 처리할 수 있어서도 안 됩니다. 새로 만든 링크를 메모리의 맵에만 보관하면 이 조건을 어깁니다.

로드 밸런서의 장애에도 대비해야 합니다. 이 글에서는 이중화된 로드 밸런서나 관리형 로드 밸런서를 사용한다고 가정합니다. 애플리케이션 인스턴스도 한 서버의 장애가 다른 인스턴스에 영향을 주지 않도록 분리해 배치합니다. 두 프로세스를 한 호스트에서 실행하면 요구사항을 충족하지 못합니다. 리전 전체의 장애와 데이터베이스 장애는 별도로 다룰 문제입니다.

예고 없이 서버가 멈추면

로드 밸런서가 5초마다 준비 상태를 확인하고, 확인에 두 번 실패한 대상을 제외한다고 가정합니다. 동작을 설명하기 위한 설정이며, 모든 배포 환경에 권장하는 값은 아닙니다. 

t0       A and B pass readiness checks.
t1       A crashes just after its last successful check.
t1..t2   Some requests still go to A and fail.
t2       A has failed enough checks; the balancer removes it.
t3       New requests go to B.
t4       A is repaired and passes the recovery checks.
t5       A re-enters the target set.

요청이 실패할 수 있는 구간은 상태 확인 사이의 어느 시점에 장애가 났는지, 확인 응답을 얼마나 오래 기다리는지, 라우팅 변경이 얼마나 빨리 전파되는지에 따라 달라집니다. 확인 주기에 실패 횟수를 곱한 값은 대략적인 추정일 뿐입니다. 선택한 로드 밸런서로 실제 구간을 측정해야 합니다.

A가 멈춰도 처리 중이던 요청이 B로 옮겨가지는 않습니다. 연결이 끊기거나 시간이 초과될 수 있습니다. 클라이언트는 조회 요청을 재시도할 수 있지만, 생성 요청에서는 V1에서 다룬 것처럼 커밋 여부를 알 수 없는 상황이 생길 수 있습니다. API가 필요한 멱등성을 보장하지 않는다면 프록시가 생성 요청을 무작정 다시 보내서는 안 됩니다.

읽기 요청도 재시도 기한을 정하고 시도 횟수를 적게 제한해야 합니다. 각 계층이 독립적으로 재시도하면 장애 중에 클라이언트 요청 하나가 수많은 시도로 늘어날 수 있습니다. AWS의 재시도 설명에서는 이런 증폭과, 제한 없이 백오프만 적용해서는 충분하지 않은 이유를 다룹니다.

상태 확인은 구체적인 질문에 답해야 합니다

준비 상태 엔드포인트는 인스턴스가 지금 요청을 받아 유효하게 처리할 수 있는지 답해야 합니다. 설정, 라우팅, 필요한 로컬 초기화를 마칠 때까지는 준비되지 않았다고 응답해야 합니다.

생존 상태 확인은 프로세스가 재시작해야 할 만큼 멈춰 있는지 확인합니다. 일시적인 데이터베이스 장애를 모든 애플리케이션 프로세스를 재시작해야 한다는 신호로 받아들이면, 의존하는 시스템 하나의 장애가 대규모 재시작으로 번질 수 있습니다.

따라서 프로세스의 생존 상태는 간단한 검사로 확인하고, 준비 상태에 따라 요청 경로를 제어합니다. 데이터베이스 연결도 모니터링해야 하지만, 공유 데이터베이스의 장애는 요청을 A 대신 B로 보내도 해결되지 않습니다. 준비 상태 확인에 데이터베이스 검사를 포함한다면 검사 제한 시간을 정해야 합니다. 모든 인스턴스가 검사에 실패했을 때 어떻게 동작할지도 정해야 합니다.

로드 밸런서의 동작은 제품마다 다릅니다. 예를 들어 AWS Application Load Balancer는 등록된 모든 대상이 비정상이면 해당 대상에도 요청을 보낼 수 있습니다. “비정상”이면 항상 트래픽을 받지 않는다고 가정하지 말고, 선택한 로드 밸런서의 동작을 확인해야 합니다.

B 하나로 전체 요청을 감당할 수 있을까요?

정상 운영 중에는 각 인스턴스가 요청의 절반 정도를 받습니다. A에 장애가 나면 B가 전체 요청을 받습니다.

이 비율로 생성 요청과 리디렉션 요청을 보내는 부하 테스트에서 인스턴스 하나가 정해 둔 지연 시간 안에 초당 80건을 처리할 수 있다는 결과가 나온다고 가정합니다. 그러면 장애 후 예상되는 초당 약 44건을 처리하고도 여유가 있습니다. 80건은 계산에 사용할 측정값의 예시이며, 이 프로젝트에서 얻은 결과가 아닙니다.

일반적으로 확인할 조건은 다음과 같습니다. 

capacity remaining after one failure >= peak admitted traffic

연결 풀도 살펴야 합니다. 데이터베이스 연결 20개짜리 풀 두 개는 연결 40개를 사용할 수 있습니다. 인스턴스를 10개 더 추가하면 데이터베이스 처리 용량은 그대로인데 연결 수는 다시 몇 배로 늘어날 수 있습니다. 전체 연결 수에 한도를 두고 인스턴스별 동시 처리량을 제한해야 합니다. 대기열이 끝없이 늘어나기 전에 초과 요청을 거절해야 합니다.

장애 전 CPU 사용량뿐 아니라 요청 경로가 바뀌는 동안의 지연 시간과 실패도 관찰해야 합니다. 남은 인스턴스의 런타임이 아직 워밍업되지 않았거나 새 연결이 한꺼번에 생기면, 이미 평상시 트래픽을 처리하던 인스턴스와 다르게 동작할 수 있습니다.

연결을 갑자기 끊지 않고 배포하기

계획된 교체에서는 A가 처리 중인 요청을 마무리할 시간을 줄 수 있습니다.

  1. 새 인스턴스를 시작하고 준비 상태가 될 때까지 기다립니다.
  2. A에 새 요청을 보내지 않습니다.
  3. 정해 둔 마무리 기한까지 A가 기존 요청을 끝내도록 기다립니다.
  4. A를 멈춘 뒤 다음 인스턴스에도 같은 절차를 반복합니다.

마무리 기한을 두면 멈춰 있는 요청 하나가 배포를 무한정 막지 못합니다. 기한이 되어도 처리 중인 요청은 실패할 수 있으므로, 애플리케이션과 로드 밸런서의 제한 시간이 서로 맞아야 합니다.

이 과정에서는 이전 버전과 새 버전이 동시에 실행됩니다. 데이터베이스 스키마를 바꿀 때도 두 버전이 함께 동작할 수 있어야 합니다. 예를 들어 코드가 새 컬럼을 사용하기 전에 필수 값이 아닌 컬럼을 먼저 추가하고, 이전 인스턴스가 모두 종료된 뒤에야 기존 컬럼을 삭제합니다. 그렇지 않으면 “롤링 배포” 중에도 서비스 전체에 오류가 날 수 있습니다.

제대로 동작하는지 어떻게 확인할까요?

A를 통해 링크를 생성하고 B를 통해 조회합니다. 이어서 요청을 보내는 동안 A를 멈추고 실패가 얼마나 오래 이어지는지 기록합니다. 배포 중에도 반복하고, 처리 중인 요청이 느릴 때와 B가 처리 용량 한계에 가까울 때도 확인합니다. 구현을 검증하기 위한 절차이며, 이미 수행한 실험은 아닙니다.

이 설계에서는 애플리케이션 서버 하나에 장애가 나면 이후 요청을 여유 용량이 충분한 다른 인스턴스로 보냅니다. 모든 리디렉션 요청은 여전히 같은 데이터베이스에 접근합니다. 캐시를 추가해도 여기서 설계한 장애 대응 방식이 개선되지는 않습니다.

V3에서는 요청량이 크게 늘어나면서 이런 데이터베이스 읽기가 다음 문제가 됩니다.
