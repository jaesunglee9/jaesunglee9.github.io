URL 단축 서비스 V4: 데이터베이스 장애에도 리디렉션 이어가기

시리즈 안내

이 글은 URL 단축 서비스 아키텍처 시리즈의 V4입니다.

  • 이전: V3
  • 다음: V5

새 요구사항

데이터베이스 서버에 장애가 나도 리디렉션은 계속되어야 합니다. 서비스가 단축 URL 생성에 성공했다고 응답하면 클라이언트는 곧바로 그 URL을 사용할 수 있어야 합니다.

V3의 한계

자주 요청하는 단축 URL이 캐시에 있으면 데이터베이스 장애가 드러나지 않을 수 있지만, 캐시에 없는 단축 URL은 여전히 사용할 수 없습니다. 생성 요청을 처리할 때도 유일한 데이터베이스 서버가 반드시 필요합니다. 캐시는 커밋된 데이터를 장애 후에도 보존하는 복제본이 아닙니다.

최소한의 설계 변경

프라이머리 데이터베이스와 읽기 복제본을 사용합니다. 

                                  +-> read replica 1
application -> cache or database +-> read replica 2
                                  +-> primary

생성 요청을 받으면 프라이머리에서 커밋합니다. 캐시에 없는 매핑은 복제본에서 조회할 수 있고, 장애가 난 복제본은 읽기 요청을 보낼 대상에서 제외할 수 있습니다. 프라이머리에 장애가 나면 데이터베이스의 장애 조치 절차에 따라 승격 조건을 갖춘 복제본을 프라이머리로 승격할 수 있습니다.

복제가 일관성에 미치는 영향

비동기 복제에서는 다음과 같은 상황이 생길 수 있습니다. 

t0  primary commits code aB3xQ9
t1  service returns the new short URL
t2  client requests aB3xQ9
t3  a lagging replica does not contain aB3xQ9 and returns no row

t3 에서 404 를 반환하면 새 요구사항을 위반합니다. 데이터베이스 커밋 후 캐시에도 매핑을 넣으면 대개 이런 상황을 줄일 수 있지만, 새 매핑을 반드시 조회할 수 있다고 보장하지는 못합니다. 캐시 쓰기가 실패하거나 항목이 캐시에서 제거될 수 있기 때문입니다.

더 강한 보장을 제공하는 정책은 두 가지입니다.

  • 복제본에서 매핑을 찾지 못하면 404 를 반환하기 전에 프라이머리를 조회합니다.
  • 동기 복제를 마친 뒤에 생성 성공을 응답합니다.

프라이머리를 다시 조회하는 방식은 일반적인 쓰기를 빠르게 처리할 수 있지만, 알 수 없는 단축 코드와 최근 생성한 단축 코드의 조회 요청이 프라이머리로 향합니다. 동기 복제는 저장된 데이터를 더 확실하게 보존하는 대신 쓰기 지연이 늘어납니다. 복제본이 확인 응답을 보내지 못하면 쓰기 가용성도 낮아집니다. 설계할 때 어느 비용을 감수할지 명확히 선택해야 합니다.

장애 조치에 필요한 처리 용량

복제가 도움이 되려면 남은 서버가 장애 조치 후 넘어오는 요청 부하를 감당할 수 있어야 합니다. 상태 확인, 승격 규칙, 연결 경로 변경, 장애에 대비해 확보한 여유 용량을 함께 테스트해야 합니다. 복구 시점 목표(RPO)에는 커밋된 데이터가 얼마나 손실될 수 있는지, 복구 시간 목표(RTO)에는 단축 URL 생성이나 리디렉션을 얼마나 오래 사용할 수 없을지 명시해야 합니다.

V4에서는 저장소 서버에 장애가 나도 동작을 이어갈 수 있습니다. 대신 서비스가 복제 지연과 장애 조치도 관리해야 합니다.
