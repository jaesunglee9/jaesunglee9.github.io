URL 단축 서비스 V4: 데이터베이스 장애에도 매핑 보존하기

캐시에 매핑이 충분히 쌓여 있으면 데이터베이스가 중단되어도 별문제 없어 보일 수 있습니다. 자주 쓰는 단축 URL로 접속하면 계속 리디렉션되지만, 방금 만들었거나 드물게 쓰는 단축 URL로 접속하면 실패합니다. 매핑을 커밋할 수 있는 곳은 여전히 데이터베이스뿐이므로 새 단축 URL 생성도 멈춥니다.

이번 글에서는 장애 후에도 데이터를 보존하는 복사본을 추가하고, 어떤 복사본이 주 서버를 대신할 수 있는지 정하겠습니다. 이어서 주 서버에 장애가 나기 직전에 만든 단축 URL을 따라가 보겠습니다. 복제가 요구사항을 실제로 충족하는지 판단하려면 이 경우를 살펴봐야 합니다.

  • 시리즈: URL 단축 서비스 아키텍처 시리즈
  • 이전 글: V3
  • 다음 글: V5

장애 시 보장할 범위 정하기

데이터베이스 서버 한 대에 장애가 나더라도 클라이언트에 생성 성공을 알린 매핑은 잃지 않아야 합니다. 클라이언트가 생성 성공 응답을 받았다면 새 단축 URL을 조회할 수 있어야 합니다.

장애를 감지하고 대체 서버를 승격하는 데는 잠시 시간이 걸릴 수 있습니다. 그동안 결과를 확인할 수 없는 요청에는 503을 반환할 수 있습니다. 모든 요청이 중단 없이 성공하거나, 데이터의 모든 복사본이 파괴되어도 데이터를 보존한다고 보장하지는 않습니다.

이 설계의 복구 시점 목표(RPO)는 서버 한 대에 장애가 난다는 가정 아래 생성 성공을 알린 매핑을 하나도 잃지 않는 것입니다. 복구 시간 목표(RTO)를 정하려면 구체적인 배포 목표를 정하고 장애 전환 절차에 걸리는 시간을 측정해야 합니다. 여기서는 복구 시간을 임의로 제시하는 대신 그 시간 동안 어떤 작업을 하는지 설명하겠습니다.

주 서버와 지정된 대기 서버로 시작하기

V3의 캐시와 애플리케이션 계층은 유지합니다. 주 데이터베이스와 대기 데이터베이스는 각각 별도의 서버와 저장 장치에 둡니다. 

application -> cache
      |
      +-> primary P === synchronous durable copy ===> standby S
      |
      +-> optional asynchronous read replica R

P는 생성 트랜잭션을 받습니다. S는 장애가 나면 P를 대신하도록 지정한 대기 서버입니다. R은 읽기 처리량을 늘리기 위해 선택적으로 두는 복제본이며, 자동으로 P를 대신할 수 있는 것은 아닙니다.

커밋 정책에 따라 생성 성공을 알리기 전에 트랜잭션의 복구 기록이 P와 S 양쪽에서 장애 후에도 보존되도록 저장되어야 합니다. 복제본이 있다는 사실만으로는 성공 응답을 보낸 쓰기 중 어디까지 그 복제본에 저장되어 있는지 알 수 없으므로 이 규칙을 명시합니다.

S를 사용할 수 없어도 P는 읽기를 처리할 수 있지만, 생성 요청은 이 정책을 충족할 수 없습니다. 클라이언트 모르게 저장 보장을 낮추는 대신 일시적인 실패를 반환합니다. 둘 중 어느 서버를 잃어도 쓰기를 계속 받아야 하는 운영 시스템이라면 복제본을 더 두고, 그에 맞는 쓰기 성공 응답 조건과 승격 정책을 마련해야 합니다.

복제본에 저장된 데이터와 조회할 수 있는 데이터의 차이

복제는 변경을 보내고 받는 단계, 복구 기록을 장애 후에도 보존되도록 저장하는 단계, 쿼리에서 행을 볼 수 있도록 변경을 적용하는 단계로 나뉩니다.

PostgreSQL은 동기 복제 설정에서 이 단계들을 구분합니다. 대기 서버에 장애 후에도 보존되는 복사본이 생길 때까지 기다렸다고 해서 모든 읽기 복제본에서 그 트랜잭션을 조회할 수 있는 것은 아닙니다. 원격 서버에서 변경을 적용할 때까지 기다리면 선택한 동기 대기 서버에서는 조회할 수 있습니다. 하지만 그와 관계없이 뒤처진 다른 복제본에서의 조회까지 보장하지는 않습니다.

생성 직후 R에서 읽으면 다음과 같은 문제가 생깁니다. 

t0  P and S durably record code A.
t1  Service returns A to the client.
t2  Client opens A; the cache has no entry.
t3  R has not replayed A and returns no row.

여기서 404를 반환하면 생성 성공을 알린 단축 URL이 존재하지 않는다고 클라이언트에 잘못 알려 줍니다. 생성할 때 캐시도 채워 두면 대개 도움이 되지만, 캐시 쓰기가 실패하거나 항목이 캐시에서 제거되면 같은 문제가 다시 생깁니다.

생성 직후 조회를 보장하는 규칙 정하기

변경되지 않는 매핑이라면 R에서 찾은 행을 사용할 수 있습니다. 하지만 행이 없다는 결과만으로는 매핑이 없다고 판단할 수 없습니다. 현재 주 서버에 확인해야 합니다.

조회 정책은 다음과 같습니다.

  1. 캐시에 매핑이 있으면 사용합니다.
  2. 캐시 미스가 나면, 읽기 복제본이 설정되어 있고 정상일 때 그곳에 쿼리합니다.
  3. 복제본에 행이 없거나 쿼리를 끝내지 못하면, 요청에 남은 시간과 읽기 허용량 안에서 현재 주 서버에 조회를 시도합니다.
  4. 최종 기준이 되는 서버에서 매핑이 없음을 확인한 경우에만 404를 반환합니다.
  5. 결과를 확인할 수 없으면 503을 반환합니다.

R이 없으면 두 번째 단계에서 바로 주 서버를 조회합니다. V3의 요청 유입 제한은 계속 적용합니다. 복제를 도입해도 주 서버로 넘기는 조회를 무제한 허용하는 것은 안전하지 않습니다.

이 정책은 P를 사용할 수 있는 동안 생성 직후 조회를 보장합니다. 매핑이 없다는 결과를 캐시하면 주 서버의 최종 확인을 건너뛸 수 있으므로, 그런 결과는 계속 캐시하지 않습니다. 존재하지 않는 코드와 최근에 만든 코드에 대한 요청은 P의 부하를 늘리므로 용량을 계획할 때 그 요청 빈도도 고려해야 합니다.

장애 전환 후에는 S가 필요한 복구 기록을 재생한 뒤에야 최종 기준이 되는 주 서버가 됩니다. 최종 확인을 위한 읽기는 S로 보냅니다. 데이터가 덜 저장된 임의의 복제본으로 같은 역할을 대신할 수는 없습니다.

주 서버 장애 과정 따라가기

클라이언트가 코드 A를 받자마자 P가 멈췄다고 가정합니다. 

1. The creation response proves P and S durably recorded A.
2. Failure detection declares P unavailable.
3. The failover controller prevents P from accepting further writes.
4. S replays the required records and is promoted.
5. Applications refresh the primary endpoint and their connections.
6. An authoritative lookup on S finds A.

세 번째 단계는 기존 주 서버가 더는 쓰기를 처리하지 못하게 막는 펜싱(fencing)입니다. 네트워크가 분리되면 서버가 멈춘 것처럼 보이다가 나중에 다시 연결될 수 있습니다. P가 여전히 쓰기를 받는 상태에서 S를 승격하면 두 서버에 서로 충돌하는 변경 이력이 생길 수 있습니다.

PostgreSQL의 장애 전환 문서도 기존 주 서버 문제와 외부 장애 감지 및 조정의 필요성을 설명합니다. 여기서는 테스트를 거친 데이터베이스 장애 전환 컨트롤러와 그 펜싱 기능을 사용합니다. 애플리케이션 인스턴스가 각자 원하는 주 서버를 독립적으로 선출하지 않습니다.

컨트롤러가 안전하게 승격할 수 있는지 확인하지 못하면 쓰기를 계속 중단합니다. 네트워크가 분리되어 상황을 확신할 수 없을 때는 가용성을 포기하고 쓰기를 처리하는 서버를 하나로 유지합니다.

P에 장애가 날 때 진행 중이던 생성 요청은 응답을 전달하지 못한 채 커밋되었을 수도 있습니다. V1에서 다룬 결과의 불확실성은 그대로 남습니다. 제품에서 생성 요청을 안전하게 재시도할 수 있어야 한다면, 장애 전환을 도입해도 멱등성이 필요합니다.

승격 후의 부하와 복구

승격된 S는 P가 처리하던 부하를 맡습니다. 애플리케이션이 다시 연결하고 캐시가 다시 채워지는 동안에도 이 부하를 처리할 수 있도록 CPU, I/O, 연결 수, 메모리를 충분히 확보해야 합니다.

예를 들어 평소 캐시를 거친 뒤 데이터베이스에 초당 읽기 2천 건과 쓰기 4백 건이 도달한다면, 승격 후에는 이 읽기와 쓰기 부하를 함께 고려해야 합니다. 대기 서버일 때 처리하던 복구 기록 재생 부하만으로는 충분하지 않습니다. 재연결이 한꺼번에 몰리고 재시도로 요청이 늘면 단기 부하는 더 커질 수 있으므로 복구 중에도 요청 유입 제어를 유지합니다.

기존 P는 새 주 서버와 상태를 맞춘 뒤 복제본으로 다시 합류해야 합니다. 예전 설정 그대로 재시작하면 안전하지 않습니다. 새 대기 서버가 데이터를 따라잡아야 두 복사본에 저장한 뒤 성공을 알리는 원래 정책을 복원하고, 그 정책에 따라 생성을 재개할 수 있습니다.

복제본과 백업도 구분해야 합니다. 실수로 데이터를 삭제하거나 잘못 갱신하면 복제본에도 빠르게 반영될 수 있습니다. 복구 절차를 테스트한 백업은 이런 종류의 장애에 대응합니다.

보장을 위협하는 상황에서 확인하기

장애 전환을 확인하려면 클라이언트가 실제로 받은 생성 응답을 모두 기록하고, P를 강제로 종료한 뒤 실제 컨트롤러로 S를 승격해 성공 응답을 받은 코드를 모두 확인하는 테스트가 유용합니다. 응답을 받지 못한 요청은 별도로 추적합니다. 이 요청들은 커밋되었을 수도, 그렇지 않을 수도 있습니다.

이어서 읽기 복제본이 뒤처진 경우, S를 잃은 경우, P가 네트워크에서 분리되었지만 계속 실행 중인 경우, 유입 제어로 허용한 부하가 가장 높을 때 승격하는 경우를 테스트합니다. 정책을 검증하기 위한 제안이며, 이 저장소에서 수행한 결과는 아닙니다.

V4는 생성 성공을 알린 각 매핑을 장애 후에도 어느 복사본이 보존하는지 정하고, 그 복사본을 어떻게 최종 기준으로 삼는지 설명합니다. 아직 데이터를 나누지는 않았습니다. P, S, R은 여전히 같은 매핑 집합을 저장합니다. V5에서는 한 주 서버에 모든 매핑을 저장하고 운영하기 어려워지는 시점을 다룹니다.
