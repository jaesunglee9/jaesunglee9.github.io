URL 단축 서비스 V1: 장애 후에도 데이터를 보존하는 최소 설계

시리즈 안내

이 글은 URL 단축 서비스 아키텍처 시리즈의 V1입니다.

  • 이전 글: V0
  • 다음 글: V2

요구사항

첫 버전에서는 트래픽이 많지 않은 URL 단축 서비스를 설계하려고 합니다. 이 글에서는 다음 요구사항을 만족하는 최소 설계를 다룹니다.

  • 매달 단축 URL 100만 개를 새로 생성합니다.
  • 평상시 트래픽에서는 생성 요청 하나당 리디렉션 요청이 약 10개 들어옵니다.
  • 트래픽이 몰리는 시간대에는 요청량이 평균의 10배에 이를 수 있습니다.
  • 단축 URL은 자동으로 만료되지 않습니다.
  • 애플리케이션을 재시작해도 데이터가 남아 있어야 합니다.
  • 서버 장애로 잠시 서비스를 이용할 수 없어도 괜찮습니다.

한 달을 30일로 잡으면 초당 평균 요청 수는 다음과 같습니다. 

1,000,000 / (30 * 24 * 60 * 60) = 0.39 creations/second
0.39 * 10                           = 3.9 redirects/second

트래픽이 몰리는 시간대에는 초당 생성 요청 약 4개, 리디렉션 요청 약 40개가 들어올 수 있습니다. 일반적인 애플리케이션 서버와 데이터베이스 하나씩으로도 처리할 만한 양입니다. 그렇지 않다고 가정하기 전에 실제 구현의 성능을 측정해야 합니다.

설계

전체 구조는 다음과 같습니다. 

client -> application -> database

데이터베이스에는 장애 후에도 보존할 매핑을 저장합니다. 

CREATE TABLE links (
    code       TEXT PRIMARY KEY,
    target_url TEXT NOT NULL,
    created_at TEXT NOT NULL
);

단축 URL 생성 요청은 다음 순서로 처리합니다.

  1. 원본 URL을 파싱하고 서비스의 URL 정책을 적용합니다.
  2. 단축 코드 후보를 생성합니다.
  3. 매핑을 삽입합니다.
  4. 기본 키 제약 조건으로 코드 충돌이 확인되면 다른 코드를 생성해 다시 시도합니다.
  5. 데이터베이스가 커밋한 뒤에만 클라이언트에 응답합니다.

애플리케이션은 표준 URL 파서를 사용하며, 호스트가 있는 절대 URL 중 http 또는 https 만 허용합니다.

클라이언트가 리디렉션을 요청하면 애플리케이션은 기본 키인 code 로 target_url 을 조회합니다. 저장된 원본 URL은 Location 헤더에 담아 응답합니다.

단축 코드 선택

데이터베이스 시퀀스를 사용하면 고유한 정수를 얻을 수 있습니다. 정수를 62진법으로 인코딩하면 길이는 짧아지지만, 인접한 값을 예측하기 어려워지지는 않습니다. 또 모든 코드를 데이터베이스에서 할당받아야 합니다.

대신 애플리케이션에서 암호학적으로 안전한 난수 생성기로 10자리 62진법 코드를 만들 수 있습니다. 가능한 코드 수는 다음과 같습니다. 

62^10 = 839,299,365,868,340,224 possible codes

코드의 고유성은 확률이 아니라 데이터베이스의 제약 조건으로 보장합니다. 난수를 사용하면 충돌이 드물어지고, 각 애플리케이션 인스턴스가 사전에 조율하지 않고 코드 후보를 만들 수 있습니다.

원본 URL을 해싱할 필요는 없습니다. 같은 입력에 항상 같은 값을 내는 해시를 사용하면 서비스 전체에 적용할 중복 제거 정책이 필요해집니다. URL의 여러 변형을 같은 URL로 볼지, 소유자와 만료일, 분석 데이터가 다른 경우 하나의 코드를 어떻게 공유할지 결정해야 합니다. 이 설계에서는 의도적으로 새로 생성하는 요청마다 별도의 단축 URL을 제공합니다.

생성 요청 재시도

데이터베이스가 커밋했지만 응답이 유실되면 클라이언트는 매핑이 생성됐는지 알 수 없습니다. 기본 설계에서는 클라이언트가 같은 요청을 재시도하면 단축 URL이 하나 더 생성됩니다.

안전한 재시도가 필요한 제품이라면 요청에서 멱등성 키를 받아 매핑과 함께 저장하고, 키에 고유 제약 조건을 걸 수 있습니다. 그러면 클라이언트가 같은 키로 다시 요청할 때 처음 생성한 단축 URL을 돌려줄 수 있습니다. 새 키는 의도적으로 새 단축 URL을 만드는 요청을 나타냅니다. 기본 요구사항에는 이 동작이 필요하지 않으므로 앞의 스키마와 생성 절차에는 포함하지 않았습니다.

저장 용량

행 하나와 메타데이터, 인덱스에 필요한 추가 공간을 합쳐 약 500바이트를 쓴다고 가정합니다. V1에서 단축 URL이 이 속도로 5년간 늘어나면 필요한 용량은 다음과 같습니다. 

1,000,000 links/month * 60 months * 500 bytes = 30 GB

이 추정치는 나중에 실제 스키마로 측정한 값으로 바꿔야 합니다. 현재 추정으로는 데이터베이스 하나로 시작하는 것이 합리적입니다.

장애 범위와 미뤄 둘 작업

애플리케이션 서버와 데이터베이스는 모두 단일 장애 지점입니다. 서버 장애로 잠시 서비스가 중단돼도 괜찮다는 V1의 요구사항에는 맞습니다. 캐시, 복제본, 샤드, 큐, 여러 리전 배포는 현재 요구사항을 충족하는 데 필요하지 않으면서 새로운 장애 유형을 늘리므로 V1에서는 미뤄 둡니다.
