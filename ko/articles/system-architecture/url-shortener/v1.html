URL 단축 서비스 V1: 장애 후에도 매핑을 보존하는 최소 설계

사용자가 긴 URL을 붙여 넣으면 단축 URL을 받아 공유할 수 있는 서비스를 설계하려고 합니다. 다음 날 애플리케이션이 재시작해도 그 단축 URL은 계속 작동해야 합니다. 첫 설계에는 매핑을 보관할 곳이 필요하지만, 아직 서버를 여러 대 둘 필요는 없습니다.

이 글은 URL 단축 서비스 아키텍처 시리즈의 V1입니다. 단축 URL 생성부터 리디렉션까지의 흐름을 따라가고, 데이터베이스가 커밋했는데도 클라이언트가 응답을 받지 못하면 어떻게 되는지 살펴보겠습니다.

  • 이전 글: V0
  • 다음 글: V2

첫 버전은 요청을 얼마나 처리해야 할까요?

설명을 위해 다음과 같이 가정합니다.

  • 매달 단축 URL 100만 개를 새로 만들며, 자동으로 만료하지 않습니다.
  • 평균적으로 생성 요청 한 건당 리디렉션 요청이 약 열 건입니다.
  • 트래픽이 몰리는 시간대에는 평균 요청량의 열 배가 들어옵니다.
  • 애플리케이션을 재시작해도 매핑은 보존됩니다.
  • 서버 장애로 서비스가 잠시 중단되는 것은 허용합니다.

한 달을 30일로 계산하면 다음과 같습니다. 

1,000,000 / (30 * 24 * 60 * 60) = 0.386 creations/second
0.386 * 10                     = 3.86 redirects/second

Busy period: about 4 creations and 40 redirects/second

이 정도라면 애플리케이션 서버 한 대와 데이터베이스 하나로 시작할 만합니다. 다만 이 수치만으로 특정 구현이 충분히 빠르다고 판단할 수는 없습니다. 예상한 비율로 요청이 들어올 때 요청 지연 시간, 데이터베이스 작업량, 연결 사용량을 측정해야 합니다.

매핑은 한곳에 보관합니다

애플리케이션은 HTTP 요청을 처리하고, 데이터베이스는 매핑을 관리합니다. 스키마와 트랜잭션 예제를 구체적으로 보여주기 위해 PostgreSQL을 사용하겠습니다. 

client -> application -> PostgreSQL
             |
             +-> HTTP redirect back to the client

리디렉션은 클라이언트에게 보내는 응답입니다. 애플리케이션이 원본 페이지를 가져오거나 그 내용을 중계하지는 않습니다. 

CREATE TABLE links (
    code       TEXT PRIMARY KEY,
    target_url TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

기본 키는 서로 다른 매핑이 같은 단축 코드를 쓰지 못하게 합니다. 원본 URL은 고유할 필요가 없습니다. 같은 원본 URL로 단축 URL을 만들려는 요청을 의도적으로 두 번 보내면, 각각 별도의 단축 URL을 만들 수 있습니다.

이 버전에서는 한번 만든 매핑을 바꾸지 않습니다. 링크 수정, 만료, 비활성화 규칙은 캐시와 악용 대응을 도입할 때 명시적으로 정해야 합니다.

생성 요청을 따라가 봅니다

클라이언트가 다음 요청을 보냈다고 가정합니다. 

POST /links
Content-Type: application/json

{"url":"https://example.com/articles/a-long-path"}

애플리케이션은 먼저 표준 파서로 URL을 파싱합니다. 초기 정책에서는 호스트가 있는 HTTP 또는 HTTPS 절대 URL을 허용하고, URL에 인증 정보가 포함되어 있으면 거부합니다. 저장하기 전에 입력 크기도 제한합니다. 파싱으로 확인하는 것은 주소 형식입니다. 원본 URL을 신뢰할 수 있는지, 앞으로도 접속할 수 있는지까지 보장하지는 않습니다.

다음으로 애플리케이션이 단축 코드 후보를 만들어 삽입을 시도합니다. 아래 PostgreSQL 구문에는 드라이버가 전달한 매개변수를 사용합니다. 

INSERT INTO links (code, target_url)
VALUES ($1, $2)
ON CONFLICT (code) DO NOTHING
RETURNING code;

PostgreSQL INSERT 문서에 따르면 충돌이 나면 삽입을 건너뛸 수 있고, 반환 절은 실제로 삽입한 행을 알려줍니다. 코드가 반환되면 이 구문이 행을 삽입한 것입니다. 결과가 비어 있으면 다른 매핑이 이미 그 코드를 사용하고 있습니다.

요청 처리 코드는 다음과 같은 짧은 반복문으로 구현합니다. 

validate the destination
repeat up to a bounded collision limit:
    generate a candidate
    begin a transaction
    attempt the insert
    if no row was inserted:
        end the transaction and try a new candidate
    otherwise:
        commit
        return the short URL only after commit succeeds
return a temporary failure if no attempt succeeds

이 반복문에서는 코드 충돌만 재시도합니다. 연결 실패나 타임아웃은 별도로 처리해야 합니다. 모든 데이터베이스 오류를 충돌로 간주해 재시도하면 장애를 감추고, 요청 처리가 끝없이 이어질 수 있습니다.

커밋에 성공하면 서비스가 클라이언트에게 다음 응답을 반환합니다. 

HTTP/1.1 201 Created
Location: https://sho.rt/aB3xQ9mN2z
Content-Type: application/json

{"short_url":"https://sho.rt/aB3xQ9mN2z"}

커밋 전에 URL을 반환하면 클라이언트가 받은 링크가 애플리케이션이 비정상 종료될 때 사라질 수 있습니다. 여기서는 데이터베이스가 커밋한 데이터를 장애 후에도 보존하도록 설정되어 있고, 영속적 저장소를 사용한다고 가정합니다. 데이터베이스가 커밋을 확인해 주더라도 실제 보장 범위는 이 설정과 저장소가 견딜 수 있는 장애에 달려 있습니다.

무작위 코드에도 고유성 제약이 필요합니다

시퀀스를 쓰면 고유한 정수를 얻을 수 있습니다. 이를 62진수로 표현하면 짧아지지만, 인접한 값을 쉽게 나열해 볼 수 있습니다.

대신 암호학적으로 안전한 난수 생성기로 ASCII 영문자와 숫자 62개 중에서 균등하게 열 글자를 뽑겠습니다. 라이브러리는 나머지 연산으로 인한 편향 없이 문자를 뽑아야 합니다. 가능한 코드 수는 다음과 같습니다. 

62^10 = 839,299,365,868,340,224 codes

V1의 생성 속도가 5년간 이어지면 매핑은 6천만 개가 됩니다. 각 후보를 균등하고 독립적으로 뽑는다면, 다음 후보가 이미 사용 중일 확률은 대략 다음과 같습니다. 

60,000,000 / 62^10 = 7.15 * 10^-11

이는 다음 한 번의 시도에서 충돌할 확률이지, 전체 기간에 충돌이 한 번도 없을 확률은 아닙니다. 충돌 자체를 불가능하게 만들 필요는 없습니다. 동시에 들어온 두 요청이 같은 후보를 골라도 기본 키 제약 때문에 매핑은 최대 하나만 삽입됩니다. 다른 요청은 새 후보를 만듭니다.

무작위로 생성하면 충돌이 드물고, 각 애플리케이션 인스턴스가 독립적으로 후보를 만들 수 있습니다. 고유성은 데이터베이스가 보장합니다. 무작위 생성이나 고유성 보장이 단축 URL의 사용 권한까지 확인해 주지는 않습니다. 공개 단축 URL을 가진 사람은 누구나 사용할 수 있습니다.

원본 URL을 해싱하는 것은 다른 문제를 푸는 방법입니다. 같은 URL에 같은 코드를 재사용하려면 중복 제거 규칙이 필요합니다. URL의 표기가 다르거나 소유자와 만료 정책이 다를 때 어떻게 처리할지도 정해야 합니다. 현재 요구사항을 충족하는 데는 이런 규칙이 필요하지 않습니다.

단축 URL로 접속해 봅니다

클라이언트가 단축 경로로 요청을 보내면 애플리케이션은 매개변수를 사용해 매핑을 조회합니다. 

SELECT target_url FROM links WHERE code = $1;

행을 찾으면 클라이언트에게 다음 응답을 반환합니다. 

HTTP/1.1 302 Found
Location: https://example.com/articles/a-long-path
Cache-Control: no-store

임시 리디렉션을 사용하고, 캐시에는 응답을 저장하지 말라고 명시적으로 요청합니다. 상태 코드 302만으로는 “절대 캐시하지 말라”는 뜻이 되지 않습니다. 이후 접속도 URL 단축 서비스에 도달해야 한다면 캐시 정책이 중요합니다. 링크 비활성화를 적용하거나 방문을 기록해야 하는 경우가 그 예입니다. 리디렉션의 의미와 no-store 지시자를 참고할 수 있습니다.

조회에 성공했지만 행이 없으면 404를 반환합니다. 조회 자체에 실패하면 503과 같은 일시적 오류를 반환합니다. 이 설계에서는 이 응답들도 캐시하지 못하게 해서 일시적 오류가 계속 남지 않도록 합니다. 데이터베이스에 연결할 수 없다는 이유로 링크가 존재하지 않는다고 응답해서는 안 됩니다.

커밋에 성공했는데 응답이 사라지면 어떻게 될까요?

매핑 저장과 클라이언트에게 URL 전달이 한꺼번에 이루어지지는 않습니다. 

1. Database commits code A.
2. Application sends the success response.
3. Connection breaks before the client receives it.
4. Client retries the creation request.
5. Database commits code B for the same destination.

두 링크 모두 유효하지만 클라이언트는 A를 모릅니다. 이것이 기본 동작입니다. 타임아웃이 발생하면 서버가 성공을 알리지 않았더라도 클라이언트는 생성 여부를 확신할 수 없습니다.

중복 생성을 허용할 수 없다면 API가 멱등성 키를 받도록 할 수 있습니다. 키, 요청의 지문, 생성한 매핑을 고유성 제약을 적용해 함께 저장합니다. 같은 키와 입력으로 재시도하면 처음 결과를 반환하고, 같은 키를 다른 입력에 재사용하면 거부합니다. 사용자를 인증한다면 키의 범위를 요청한 사용자별로 구분합니다.

키를 얼마나 오래 보관할지도 정해야 합니다. 키를 지우고 나면 같은 요청으로 다시 링크를 만들 수 있기 때문입니다. V0에서는 생성 요청마다 새 매핑을 허용하므로, 여기서는 이 변경을 미룹니다.

운영하려면 무엇이 필요할까요?

행 하나와 메타데이터, 그 행이 차지하는 인덱스 공간을 합쳐 500바이트라고 가정합니다. 저장 용량을 추산하기 위한 가정이며, 앞의 스키마를 측정한 값은 아닙니다. 

1,000,000 links/month * 60 months * 500 bytes = 30 GB

긴 URL과 데이터베이스가 추가로 사용하는 공간 때문에 결과는 크게 달라질 수 있습니다. 실제 데이터를 대표할 만한 행과 인덱스를 측정한 뒤, 로그, 유지보수, 백업, 데이터 증가에 필요한 여유 공간을 확보해야 합니다.

이 설계를 믿고 사용하기 전에, 대응한다고 설명한 장애 상황을 검증해야 합니다. 생성에 성공한 뒤 애플리케이션을 재시작하고, 코드 충돌을 강제로 일으키고, 커밋 도중 연결을 끊고, 조회 중에 데이터베이스를 사용할 수 없게 해봅니다. 이는 앞으로 수행할 검증 항목이며, 이 글에서 벤치마크나 장애 실험을 수행했다고 주장하지는 않습니다.

영속적 저장소에도 복구 계획이 필요합니다. 백업을 만들고 복원 과정을 검증해야 실수나 저장소 손실에 대비할 수 있습니다. 애플리케이션 재시작 테스트만으로는 이런 상황을 확인할 수 없습니다. 배포 전에 허용할 데이터 손실량과 복구 시간을 정해야 합니다.

이 단계에서는 애플리케이션 서버가 중단되면 복구될 때까지 모든 링크에 접속할 수 없습니다. 매핑이 온전히 남아 있어도 서비스는 중단될 수 있습니다. V2에서는 이 장애에 대응합니다.
